Add the third MCP write tool: `cancel_action_run`, cancelling a pending or running Actions workflow run behind its own switch.

The first batch of write tools was `create_issue_comment` and `submit_pull_review`; the decision record reserved `cancel_action_run` as the first candidate of a second batch, with a switch of its own. It ships now as that candidate, and its switch is `forgejoToolkit.mcpWriteTools.cancelActionRun` — **off by default and independent of the other two**: turning it on enables no other tool, and turning either of them on leaves this one refused with its own setting named. The gating is the same two gates as the first batch, with no new machinery: VS Code asks before every call (the tool declares no `readOnlyHint`, and no `destructiveHint` either), and only a session the extension host itself established may write. Anything else — a zero-configuration launch, an anonymous server, a static `mcp.json` that only carries your own token — gets a plain refusal naming the setting, as a normal tool result rather than an error, so an agent stops and asks instead of retrying.

This is the first write tool whose effect is a **stop** rather than an appended record. It cancels the run's pending and running jobs; it cannot be undone by the tool, and triggering the run again is a separate operation it does not perform. Forgejo's cancel endpoint is a body-less `POST` that answers `204` with no content — and it answers `204` for a run that had already finished, where it cancels nothing — so the result says the server accepted the cancel request and points at `list_action_runs` for the run's actual state, instead of claiming a state change the tool cannot observe. Being body-less, its audit line carries **no** `bytes` or `sha256` (absent, not zero — the same rule a body-less `COMMENT` review already follows), and it has no `reviewId`.

It reuses the machinery the first batch shipped rather than copying it: the same two gates and validation order, the same `dryRun` plan (which names the run number, the endpoint and what cancelling means, and sends nothing), the same per-session idempotency table (10 minutes / 32 entries, now keyed by tool, target and run number) and the same audit line. A repeated cancel with the same key and the same run inside the window replays the earlier result — the second cancel is the same logical action — while the same key across tools or for a different run is refused. A retry that does not reuse the key cannot double-cancel anyway, because the server leaves a finished run unchanged.

The tool surface grows from 32 to 33 tools (30 read-only plus three write). `rerun_action_run` still waits for Forgejo 17 to expose the endpoint, with a hand-written web route explicitly rejected. The host-side modal confirmation for broker sessions is not a missing piece of this batch and will not follow it: that stage was one of the optional additions the decision record listed for the user who turns VS Code's per-call approval off, and the maintainer decided against building it on 2026-10-02 (§9 of that record), leaving the reasons and the three preconditions on file.
