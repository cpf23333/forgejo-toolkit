Read the `X-Total-Count` response header on the paged list endpoints, so truncation reporting is exact whenever the server reports a total: a list of exactly 500 items whose total agrees no longer shows a "may be incomplete" notice, and a total above the loaded rows proves the list was actually cut. The header is read on both sides of the extension — every list the client pages itself, behind the existing methods that now return the client's `PagedList` shape or gained a `*WithTotal` sibling: the user's repositories and repositories searched for cloning, a repository's branches, tags, releases, labels and milestones, its issues and pull requests (both the unfiltered listing and the keyword-filtered one through the issues endpoint), a pull request's changed files, commits, reviews, and its comment/event timeline, a file's commit history, a run's artifacts, and the authenticated user's notifications. The notification poller now pages precisely — `ceil(total / page size)` requests with no empty look-ahead page — when a total is reported, and a non-empty page that matches the total counts as the whole unread set. The MCP tools carry the total into their results rather than dropping it: the tools whose whole result is a paged list answer `{ items, totalCount }`, the ones that wrap lists inside a larger result name the total beside the list (`commentsTotalCount`, `filesTotalCount`, `commitsTotalCount`), and `get_pr_review_brief`'s `reviewStatus.truncated` is decided the same way. Instances that omit the header keep the previous length-based heuristic everywhere, unchanged.
