Add the first MCP write tool: `create_issue_comment`, gated twice, with a dry run, an idempotency key and an audit line.

The MCP surface has been read-only so far, and the human-in-the-loop guarantee rested on the tools themselves — every one mapped to a `GET`, so VS Code skipped its per-call confirmation. A tool that changes server state cannot keep that arrangement, so it is built the other way round: it declares no `readOnlyHint`, which makes VS Code show its confirmation dialog (and lets the user edit the parameters there) before the call is sent at all, and it additionally requires an explicit opt-in through a new per-tool setting, `forgejoToolkit.mcpWriteTools.createIssueComment`, **off by default**.

Being off by default is not enough on its own, because the headless MCP process cannot read extension settings and a statically launched server may carry a token someone wrote into their own `mcp.json` by hand — a session like that would otherwise write while having bypassed both the switch and the audit. So the second gate is provenance: a write is only possible in a session the **extension host itself** established (a definition the extension provides, or a static launch forwarded into the host's local broker, where the real tool logic runs with the token). The host marks such a definition with `FORGEJO_MCP_WRITE_TOOLS`, and the broker recomputes what a session may write from its own settings rather than trusting anything in the handshake, so a hand-written value in a static configuration widens nothing. Any other session — zero-configuration, anonymous, or carrying a token from the user's own file — gets a plain refusal naming the setting to turn on, as a normal tool result rather than an error, so an agent stops and asks instead of retrying.

The tool itself appends exactly one comment and changes nothing else. `dryRun: true` returns the plan (instance, repository, target, body length, bytes, digest, endpoint) and sends no request, which is what the description tells an agent to do before a batch. An optional `idempotencyKey` makes a retry safe for ten minutes: the same key with the same target and body replays the earlier result instead of writing a second comment, while the same key with a different target or body is refused. Forgejo has no server-side idempotency on this endpoint, so a retry that does not reuse the key still duplicates, and the description says so. The tool refuses an empty or oversized (over 64 KB) body before anything is sent.

Every write call is audited — success, HTTP failure, refusal, duplicate and dry run alike — as one JSON line naming the timestamp, caller, instance, repository, target, tool, dry-run flag, body byte count and SHA-256, result and duration. The comment text is never recorded. The line goes to the `Forgejo Toolkit` Output Channel; the new `forgejoToolkit.mcpWriteAuditToFile` setting (off by default) additionally appends the same line to `mcp-write-audit.jsonl` under the extension's log folder, capped at 1 MB with two rolled files. The log is per window, and a broker session's records land in whichever window currently owns the broker.

`submit_pull_review` — the second tool of the first batch — is not part of this change, and its switch is contributed by the changeset that ships that tool rather than here: the decision record fixes both names, but a setting whose tool does not exist must not be user-visible. `rerun_action_run` is still unattempted and waits for Forgejo 17 to expose the endpoint. The host-side modal confirmation for broker sessions is **not** pending: it was deliberately decided against on 2026-10-02 (§9 of the decision record) — VS Code's per-call approval plus each tool's own switch cover the normal configuration, and the modal would have cost a cross-window route with a timeout semantics for the case where the user has already turned that approval off.
