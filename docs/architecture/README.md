# Architecture

This document describes the high-level architecture of Forgejo Toolkit.

## Overview

Forgejo Toolkit is a VS Code extension with a Webview-based user interface. It is organized as a pnpm workspace monorepo:

- `packages/forgejo-toolkit` — VS Code extension host.
- `packages/forgejo-api` — Generated Forgejo API client.
- `packages/shared` — Shared HTTP client and common types, plus the wire schemas both sides of a boundary have to agree on: the webview message union (`src/webview/messages.ts`), the MCP on-disk records (`src/mcp/workspaceState.ts` — `McpWorkspaceStateFile`, `McpInstanceRegistryFile`, `McpBrokerRegistryFile`), `src/git/url.ts` and `src/limits.ts`.

## Extension host

The extension host is written in TypeScript and bundled with Rolldown. It is responsible for:

- Registering the webview view (`forgejoToolkitView`, a `webview`-type view in the `forgejoToolkit` activity-bar container, registered with `registerWebviewViewProvider`), commands, and the standalone webview panels.
- Managing VS Code configuration and secrets.
- Running Git worktree commands for PR checkouts.
- Forwarding messages between the webview and the Forgejo API.

## Webview UI

The webview UI is a Vue 3 single-page application built with Vite. It communicates with the extension host through the VS Code webview message API and renders the dashboard, repository details, issues, pull requests, and settings.

Every surface (the sidebar dashboard, the settings tab, the onboarding panel, the review-comment editor and the AI pre-review panel) is mounted through `mountSurface()` in `packages/forgejo-toolkit/webview/src/boot.ts`, which is also where the shared context-menu policy is installed, so no view has to remember it. The platform's default editing menu (Cut / Copy / Paste) says nothing about a repository, pull request, issue or notification row, so it is suppressed by default and kept only on the webview's own controls — an `input`, a `textarea`, a `contenteditable` editing host, the fields inside the `vscode-*` components' shadow roots, and CodeMirror's editing surface, whose hidden textarea is re-pointed under the pointer from inside the `contextmenu` dispatch — and on a non-empty text selection. The predicate is `allowsNativeContextMenu()` and the listener `installNativeContextMenuPolicy()`, both in `packages/forgejo-toolkit/webview/src/utils/nativeContextMenu.ts`. Keeping that suppression is conditional on it never taking away something the reader needs, and that condition was measured in the isolated dev host (2026-10-06, both builds, `--ai-mock`): a plain row and a plain card are suppressed — the policy's own capture listener sees `defaultPrevented` and no menu appears — while an `input` inside a `vscode-textfield` shadow root, a line of the CodeMirror comment editor and a non-empty text selection all keep it, because the policy leaves the event alone and VS Code's own webview handler then opens the menu. The owed edge of the non-empty-selection exception — a selection made inside a shadow root — holds too: a real drag inside a shadow tree reads its text back from `getSelection().toString()` and the menu stays, so the fallback below was not needed. What that measurement also settled is that an empty `toString()` tracks **selectability**, not the shadow tree: it returns the text for a `user-select: text` node inside a shadow root and an empty string for a `user-select: none` one, in light and shadow DOM alike, and every text node this webview renders inside a shadow root is `user-select: none`, so a reader cannot select the case that would fail. Should a later change make the exception unusable, the fallback is unchanged: **re-enable the context menu** — withdrawing the suppression for the affected case, or the whole suppression when the case cannot be told apart — rather than ship a policy that takes copy away.

That suppression is deliberately interim. The rows are meant to carry VS Code-native items, contributed with `contributes.menus` under `webview/context` and aimed at the element under the cursor with `data-vscode-context`; those items have to be **added** rather than the suppression re-enabled, because the menu being suppressed is the wrong menu rather than a menu that is missing something. Adding them therefore means letting the menu through where a contribution applies — either by narrowing the predicate or by switching to `preventDefaultContextMenuItems`, VS Code's key for hiding only its own Cut / Copy / Paste entries — and the two exceptions above are what the added items must not break. The deferred inventory is in `TODO.md`.

The sidebar's view title carries one refresh action per page, and it refreshes the data of the page the reader is on. A command's title in a menu is static, so the tooltip that says the true thing has to be a command of its own: five `view/title` commands share the `$(refresh)` icon and one handler (`ForgejoToolkitViewProvider.refresh`, registered from `REFRESH_VIEW_COMMANDS` in `packages/forgejo-toolkit/src/webview/activeView.ts`), and their `when` clauses are mutually exclusive, so exactly one is visible for the page on screen — the dashboard's instances and repositories, a repository (its detail, its issue and pull request lists, one run), one issue, one pull request, or the notification list. VS Code cannot see a webview's route, so those clauses test `forgejoToolkit.activeView`, which the host fills from what the sidebar reports (`setActiveView`, posted from the route hook `packages/forgejo-toolkit/webview/src/composables/useAppState.ts` already keeps for its own caches, through `activeViewForRoute`; only a webview that has a router reports at all, which is why the settings tab and the four standalone panels can never move the key); the vocabulary is `FORGEJO_ACTIVE_VIEWS` in `packages/shared/src/webview/messages.ts`, shared by both sides so they cannot drift, and the host validates every report because a webview is untrusted. The context key is cleared while the webview has not reported and again when it is disposed, so no item can fire for a page the host cannot name — there is no fallback icon, and the palette entries are gated the same way. Where a refresh would mean nothing the webview reports `FORGEJO_NO_ACTIVE_VIEW` instead and no clause matches it: that is the dashboard of an installation with no instance, which is also the sidebar's first-run state. The global search page deliberately has no item — its results belong to the query in its own box, and re-running that query is what its Search control already does. The settings tab, the setup wizard, the review-comment editor and the AI pre-review panel are separate editor-area documents with no view title bar and no router, so they never report a view and no item is contributed for them. Walked in the isolated dev host (2026-10-06): the title bar carried exactly one refresh item per route — 刷新实例与仓库 on the dashboard, 刷新此仓库 for a repository's detail, its issue list, its pull request list and one action run, 刷新此议题 on an issue, 刷新此 Pull Request on a pull request and 刷新通知 on the notifications page — the command palette filtered to 刷新 listed only that one for the route on screen, the global search page contributed none, and with either editor-area panel focused the sidebar's own item was still the only one. A press re-issues the view's own load rather than the instance list: on the notifications page the extension's output channel took 25 `GET /api/v1/notifications` requests in one burst at the press, one per configured instance. The same run covered the first-run wizard's status region: with nothing to report it is 0x0 with no padding and no background — the gap between the Test/Add buttons and the Previous/Next row is the wizard's own 32 px — and a connection test that reports something brings the band back in flow at 600x33 px with `padding: 8px 12px` and the section background, which pushes that row down by the band's height.

The press is one path, not one per page. `refresh()` in `viewProvider.ts` drops the host's repository-content memos, re-pushes the instance list and posts `refreshData`; the webview routes that from its own route (`refreshActiveView` in `packages/forgejo-toolkit/webview/src/composables/useAppState.ts`). The dashboard and the repository issue and pull request lists keep the instance-level refresh they always had — dropping the instance TTL caches, replaying the held list requests — while every other covered view re-issues the loads it owns, because a repository's selected branch, an action run's expanded job logs and the notification filters on screen are the view's own knowledge rather than the composable's. That handover is a signal the views answer through `useViewRefresh()` in `packages/forgejo-toolkit/webview/src/composables/viewRefresh.ts`, which is also where the "only the view whose route is the current one re-reads itself" rule lives once instead of in each view. A `refreshData` that arrives with no route at all keeps the dashboard behaviour.

## API layer

The `forgejo-api` package is generated from the Forgejo OpenAPI specification using Kubb. It exports typed operations (each taking one grouped `{ path, query, body, client, … }` options object) and MSW handlers for testing, and exposes Kubb's bundled client core through its `./kubb` subpath. The `shared` package provides a thin transport that merges headers, encodes the body and parses responses; `packages/forgejo-toolkit/src/api/sharedTransport.ts` wires it in as the transport of the generated client, so the generated operations send through the shared layer without a line of generated code being rewritten. Authentication is not part of either: the extension host's `ForgejoClient` adds `Authorization: token <token>` (see [api-client.md](./api-client.md)).

## Design documents

Documents under [`docs/design/`](../design/) record decisions **at the moment they are made** — the problem, the chosen approach, the rejected alternatives and the evidence that would change the decision. A design document is a decision record, not a status field: some of those decisions have since shipped, and the architecture pages above are where the shipped behaviour is described. A shipped design is not reduced to a pointer: the matching architecture page describes the mechanism the code now implements, while the design document stays the decision record and the home of its own measurements — the soak numbers and symbol-level assertions in [multi-window-polling-lease.md](../design/multi-window-polling-lease.md), for example, are cited by [window-coordination.md](./window-coordination.md) rather than repeated there.

- [MCP Phase 2 write tools: the confirmation model](../design/mcp-write-tools-confirmation.md) — per-tool settings defaulting to off, no `readOnlyHint` (VS Code's own tool approval becomes the first gate), refusal instead of anonymous fallback when no extension host is running, idempotency, dry-run, audit trail. **Implemented** for the first batch (`create_issue_comment`, `submit_pull_review`) and for batch 2's `cancel_action_run`; see [mcp-server.md](./mcp-server.md). The host-side modal confirmation (stage 3) was **deliberately decided against on 2026-10-02**, not forgotten — the record keeps the reasoning and the preconditions that were dropped with it.
- [Multi-window "one window leads" polling lease](../design/multi-window-polling-lease.md) — **implemented**, see [window-coordination.md](./window-coordination.md): a `globalStorage` lease file claimed with an atomic `fs.open(…, 'wx')` instead of a `globalState` timestamp, heartbeat/expiry versus the poll interval, handover on `deactivate()`, and the rule that every failure degrades towards polling rather than towards silently not notifying.
