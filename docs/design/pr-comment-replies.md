# PR 评审评论的回复（网页格式）

- 状态：**已交付**。回复入口、正文格式，以及"回复 = PR 时间线里的普通评论"的写入路径都已落地。
  写入路径在 **2026-10-02** 由"追加进待提交评审"改为"发成 issue 层的普通评论"，理由与实测证据见 §2。
  正文在 **2026-10-02** 有两处修正：归属行从"我们自己加 `> ` 前缀的引用行"改回**平台自己的写法**
  （不带 `> ` 的普通行，见 §1.3），顺序由"引用块在前"改为"回复正文在前"——因为实例首页活动流的摘要
  就是正文的**第一行**，引用在前会让它显示被回复者的话而切掉用户自己写的。实测证据、代价、废弃的原文
  与记下不采用的替代见 §1。

- 适用范围：**回复一条已有的 PR 行级评审评论**这一件事。不含新建评论（那是既有的
  `forgejoToolkit.addPullReviewComment`）、不含提交评审、不含评审结论。

- 关联：[`ai-prereview.md`](./ai-prereview.md) 的「现状摘要」一节（AI 预评审的草稿落进待提交评审，
  是**另一条**写入路径；2026-10-02 之后两条路径彼此独立，回复不再经过它）；
  [`mcp-write-tools-confirmation.md`](./mcp-write-tools-confirmation.md)
  的写侧约束是同一批"只写中间态、公开仍由人按下按钮"的先例。

- 基线代码：写作代码在 `src/comments/pullReviewCommentController.ts` 的 `replyToComment`、
  `src/comments/reviewReply.ts` 的 `buildReviewReplyBody`、`src/comments/pullReviewReplyTarget.ts`

  2026-10-02 之前回复经 `src/aiPreReview.ts` 的 `writePendingReviewComment` 落地，该助手已随本次修正
  删除。工作树里可能有其他 agent 的在途改动，**行号会漂移**，所以本文一律给**可搜索的符号名**，不给行号。

## 现状摘要

- **入口**：线程里 VS Code 自带的回复框。`canReply` 在每次渲染时都为 `true`，所以每条评论都能被
  回复。回复框用 VS Code 自带的措辞——一条回复就是一条公开的 PR 评论，正是它自己的 "Reply…" 与
  提交按钮所描述的东西。（2026-10-02 修正：此前把 `CommentController.options` 的提示语改成
  「Reply as a pending review comment...」，因为那时的回复写的确实是待提交评审里的草稿；写入路径
  改掉之后那句话不再成立，这个覆盖已删除。）

- **谁被回复**：线程的 `contextValue`（`encodePullReviewReplyTarget`）带的是**锚点**
  （实例、仓库、PR、path、行号、`extra_lines_count`、哪一侧），不是评论 id。一个锚点上的所有评论
  渲染成同一个线程——这正是网页端"一个锚点一段对话"的形状——被引用的是这个线程里的最后一条评论，
  而锚点用来定位是哪个 PR 并重校验那条评论还在不在 diff 上（回复本身已经不带锚点，见 §2.1）。

- **正文**：见 §1。**回复正文在最前、引用块在最后**（顺序与平台相反，为的是让实例首页活动流这类只取
  正文**第一行**的消费者显示用户自己写的话）；归属行是**平台自己的写法**（`@作者 wrote in <评论 URL>:`
  一条普通行，不带 `> `）；引用的原文用**未渲染**的纯文本（`_commentQuoteSources`），不是线程里那段
  `MarkdownString`（它已经被硬换行和附件 URL 改写过了，引用回去就不是用户写的话）。

- **落到哪里**：见 §2。发成 PR 时间线里的**普通评论**（issue 层的评论端点），**从不**写进待提交
  评审，也**从不**提交任何评审。

- **在 VS Code 里要看得见自己刚发出的回复，靠的是本地回显**：diff 线程渲染的是评审评论（review
  comments），而回复是 issue 层的普通评论，所以它出现在 PR 的时间线（网页端、本扩展的 PR 详情页）
  而不是这个线程里。这是"回复 = 对话而不是评审内容"的直接后果；为了不在按下回复后"什么都没发生"，
  成功之后把回复**本地回显**进刚才那个线程（见 §3）。

## 1. 决定：回复正文在前，其余照平台的形状

**Forgejo 没有"回复"这个对象。** ~~网页端的"引用回复"就是发一条普通评论。~~ 2026-10-02 修正：它发的
是一条**评审评论**，只是带 `origin=timeline` 落在 PR 时间线上（§1.4），正文由客户端拼出来（§1.1）。
维护者在实例上抓到了网页端自己发出的那条引用回复（评论 125）的 `content`，形状是：

```
@<作者登录名> wrote in <被回复评论的绝对 URL>:
<空行>
> <被引用正文，逐行加 "> " 前缀>
<空行>
<回复正文>
```

归属行是一条**普通行**（没有 `>`），引用块是紧随其后、独立的 blockquote，回复正文在最后。本功能照抄
其中的每一块——同样的归属行文字、同样的逐行 `> ` 引用、同样的单个空行——**只把顺序倒过来**：

```
<回复正文>
<空行>
@<作者登录名> wrote in <被回复评论的绝对 URL>:
<空行>
> <被引用正文，逐行加 "> " 前缀>
```

- 归属行：`@${author} wrote in ${absoluteUrl}:`，其中 URL 是
  `<实例>/<owner>/<repo>/pulls/<n>/files#issuecomment-<id>`（`_commentUrl` 按同一形状拼）。
  `REVIEW_REPLY_ATTRIBUTION_PREFIX` / `..._MIDDLE` 就是这两个字面量，**不带 `> ` 前缀**，与平台一致。
- 引用块（本功能把它放在正文末尾）：`quoteMarkdownLines` 给原文每一行加 `> `。引用的是**未渲染**的
  纯文本（见「现状摘要」），空行也照引（渲染成 `> `）。
- 顺序是我们**唯一的偏离**：回复正文是正文的**第一行**，引用块在最后。理由见 §1.1，代价见 §1.2。

否掉的方案（含本轮新增的两条）：

- **~~把 `> ` 加在归属行前面~~**：这是我们原来的写法，让归属行与引用块连成一个 blockquote。它不是
  平台的形状——平台的归属行是普通行（评论 125 的 `content`）——本轮已改回平台写法。
- **~~沿用平台的顺序（引用块在前）~~**：实测证明它会让实例首页活动流显示被回复者的话（或归属行），
  而切掉用户写的，见 §1.1。
- **~~只发回复正文~~**：网页端会把一个没有引用的评论渲染成孤立发言，读的人不知道它在答什么。
- **~~引用渲染后的 `MarkdownString`~~**：那是硬换行 + 附件 URL 重写之后的产物，引用回去等于替用户
  改了原话。
- **~~给评论加 `replyTo` 之类的自定义字段~~**：平台没有这个字段，写进去只会被忽略或报错。

### 1.1 为什么改：首页活动流的摘要就是正文的第一行（实测证据）

机制（读到的服务端行为，不是推断）：实例首页活动流渲染 `templates/user/dashboard/feeds.tmpl:113-118`，
评论那一支渲染的是**活动行里存的摘要**（`GetIssueInfos[1]` 所取的 `content`），而不是评论正文本身；这个
摘要由 `services/feed/action.go:544-565` 的 `abbreviatedComment()` 在写入时切出来：先
`strings.Split(comment, "\n")[0]` 取**裸 `\n`** 的第一行（行尾的 `\r` 因此会留下来），首行以代码围栏
开头时返回空串，其余交给 `modules/util/truncate.go:17-40` 的 `util.SplitStringAtByteN(firstLine, 200)`：
按**字节**截到 200 以内，断口落在 15 字节内的空格时退到那个空格再补 `…`。写入侧的四个调用点
（`services/feed/action.go:249`、`340`、`356`、`413`）都走它，再经 `encodeContent` 存进活动行。
**没有任何代码路径会去掉引用块或归属行，也没有"跳到后面某一行"这类入参**：`abbreviatedComment` 是纯
函数，入参只有评论正文一个字符串。摘要还是**写入时的快照**——`services/notify/null.go:80-82` 的
`UpdateComment` 是空占位，`actionNotifier`（`services/feed/action.go:47-49`）嵌的就是它且没有覆写，
所以**编辑评论永远不会刷新那一行**。

以上行号来自本机那份 **Forgejo 开发克隆**（development clone；分支 `forgejo`、HEAD `62c6d1c`，该克隆
**没有 tag**），它们钉在某个修订上、不会随工作树漂移；克隆的行为复现了下面实测的 16.0.2 那几行。本文对
自己工作树里的 `src/` 仍只给符号名。读 `/repos/<owner>/<repo>/activities/feeds` 得到的实测：

- 行 **580**（`comment_pull`，评论 **123**，我们旧的"引用在前"回复）：`comment.body` 是我们的完整正文，
  而摘要 `content` 只有第一行 `> @cpf23333 wrote in …#issuecomment-103:`。
- 行 **577**（一条引用在前、但不是本扩展发出的回复，4 行、回复文字 `111`）：同样只存第一行，连 `\r`
  都保留——这是"按 `\n` 切第一行"的直接证据。
- 行 **582**（`comment_pull`，评论 **125**，**网页端自己**发出的引用回复）：摘要只有
  `@cpf23333 wrote in …/pulls/11#issuecomment-124:\r`。**平台自己的引用回复在首页活动流里也只显示
  归属行**，因为它的正文同样是引用在前。
- 行 **581**（评论 **124**，维护者早先那条正文只有 `12345`、不带引用的回复）：摘要是 `12345`——它当时
  看起来"正常"的唯一原因，是那条正文里根本没有引用。

结论：规则对全平台一致，**决定读者在首页看到什么的就是正文的第一行**。"维护者自己在网页端回的那条显示了
他的话"这个印象来自上面那条**不带引用**的评论（124）；平台自己的引用回复同样会被摘要成归属行（125）。

顺序这个决定在机制上有多少余地，三条说完：

- **（a）照平台的顺序（引用在前），首页那一行就只能显示归属行。** 平台自己就是这么写的，活动行 582 正是
  这个结果；这不是我们的实现问题，而是"摘要取第一行"这条规则本身。
- **（b）没有任何受支持的字段、参数、端点或正文版式能改变它。** 摘要只由正文第一行决定（上面的
  `abbreviatedComment`），而 API 连"回复"都表达不了：`modules/structs/pull_review.go:75-96` 的
  `CreatePullReviewComment` 只有 path/body/`old_position`/`new_position`/`extra_lines_count`，评审 id
  只能从 URL 拿到（`routers/api/v1/repo/pull_review.go:354`），`POST …/reviews` 干脆写死
  `0, // no reply`（同文件 `:529`）；`models/issues/comment.go:244-334` 的 `Comment` 也没有 reply-to
  字段（见 §1.4）。
- **（c）所以正文顺序是唯一的杠杆，而它在服务端不花任何代价。** 我们偏离的只是平台那一侧的**客户端约定**
  （`web_src/js/features/repo-legacy.js:610` 在浏览器里把归属行拼进编辑框），服务端对"引用在前"没有任何
  状态；写入对象、端点、存储字段一个都没动（§2.1），改变的只有那一行摘要显示谁的哪句话。

### 1.2 代价与取舍

- **代价**：正文顺序**有意**与平台自己写出的那条不同，所以"我们的回复与网页端自己写的完全一样"这句话
  不再成立——**只有顺序不同**，其余逐字一致（归属行文字、两个空行的位置、逐行 `> ` 引用）。
- **收益**：任何做摘要的消费者（实例首页活动流、通知、邮件、移动端）显示的都是**用户自己写的话**，
  而平台自己的引用回复在这些地方显示的是归属行（行 582）。引用块仍在正文末尾，网页端照常把它渲染成
  引用，读的人依旧看得出在答哪一条。
- **为什么不反过来（把回复放在引用块之后）**：那就是平台的顺序，已被行 577/580/582 的实测否掉；引用
  在前时，摘要位必然被别人（或归属行）占满。
- **开头是空行也要挡住**：`replyToComment` 只要求正文 trim 后非空，所以 `"\n\nhello"` 是可能的输入；
  原样拼进去第一行就是空行，而 `feeds.tmpl` 又用 `{{if $comment}}` 判断摘要，那一行会**一个字都不
  显示**。`buildReviewReplyBody` 因此先去掉回复正文开头的空行（只去开头，回复内部的空行不动）。

## 2. 决定：回复发成 PR 时间线评论，待提交评审只留给 AI 草稿

**2026-10-02 修正：本节原先的决定（复用 `writePendingReviewComment`，把回复追加进待提交评审）
已废弃。** 原文保留在 §2.5，理由与实测证据见 §2.3、§2.4。当时的判断把回复和 AI 草稿当成"同一个
动作的两种触发方式"，忽略了回复是**对话**、草稿是**待公开的评审内容**——这两件事对可见性的要求相反。

### 2.1 现在的决定

- **回复 = 评论的评论 = 对话，不是评审内容。** 它经 `src/api/client.ts` 的 `createIssueComment`
  发出，即 `POST /repos/{owner}/{repo}/issues/{index}/comments`：Gitea/Forgejo 的 PR 就是 issue，
  这一条端点同时服务两者，也是网页端自己发**普通评论**所走的端点（它发**回复**时用的是 review-comments
  端点加 `origin=timeline` 与 `reply=<id>`，见 §1.4）。因此回复**立即可见**，不需要提交任何评审，也不
  需要选结论。
- **待提交评审只归 AI 预评审的草稿。** "只写中间态、公开由人按下按钮"这条承诺因此只对 AI 草稿
  成立：草稿写进待提交评审，**在用户提交评审之前对别人不可见**；回复则一开始就是公开的对话。
  两条写入路径自此完全分开。
- **原配套决定里"待提交评审的查找沿用交互路径的判定"随原决定作废**：回复不再查找待提交评审，
  `src/aiPreReview.ts` 的 `writePendingReviewComment` 因此没有调用方，已删除（AI 草稿路径
  `writePreReviewDrafts` 一行未动）。其余约束见 §2.2。

### 2.2 保留下来的约束

- **写入前先重校验锚点**：拿 PR diff 的行表核对线程带来的 path/行号/区间/侧。行（或区间的尾行）
  已经不在 diff 里（强推、文件不再出现）就**拒绝**并说明，绝不挪到旁边的行。回复虽然不再带锚点，
  但"要回答的那条评论还在不在这个 PR 的 diff 上"仍然是这条拒绝的理由。
- **引用对象必须还在线程里**：要引用的那条评论必须仍从这个线程的 `contextValue` 解析出 context 与
  纯文本原文，否则拒绝发布——绝不发一条不知道在答什么的评论。
- **失败要看得见，且不留幻影评论**：POST 失败时弹出错误、**不**重渲染线程（重渲染会丢掉用户正在
  看的输入），也不会留下任何看起来发出去了的评论。

### 2.3 为什么改

- **待提交评审里的评论在时间线里看不见**：它要等用户**提交**那次评审才公开。回复本意是对话，却因此
  静默地停在一个只有自己看得到的草稿里。
- **让一条回复变得可见，代价是提交一次评审并选一个结论**（`COMMENT` / `APPROVE` /
  `REQUEST_CHANGES`）。这会凭空产生一次评审记录与一个立场，把"回答一句话"变成"对这次 PR 表态"。
- **草稿位只有一份**：Forgejo 每个用户每个 PR 只允许一条待提交评审。回复混进去以后，用户自己的草稿
  与 AI 草稿、回复挤在同一个待提交评审里，而"这条回复什么时候公开"取决于用户何时提交那份草稿。

### 2.4 实测证据（维护者的实例）

- 在 VS Code 里回复 `cpf23333/test#11` 的一条评审评论：回复落在**待提交评审 21** 里、成为其中的
  评论 **121**，因此**从未**出现在网页端的时间线里——要让这条回复可见，就得提交那次评审。
  （那次误放的评审与评论随后由维护者删除。）
- 同一位用户在网页端回复一条**时间线**评论（issue #9）：那是普通评论，**立刻**出现在时间线里。
- 两条记录指向同一件事：可见性由**写入端点**决定，而不是由正文形状决定——发成 issue 层的普通评论
  就立刻可见，写进待提交评审就看不见。
- 本节说的是**可见性**；首页活动流**摘要**只取正文第一行那一组实测（行 580 对评论 123、行 577、
  行 582 对评论 125）在 §1.1，两者互不冲突：端点决定这条评论在不在时间线上，正文顺序决定它在摘要
  位置显示谁的哪句话。

## 3. 决定：回复在本地回显到被回复的那个线程（仅限本次会话）

**2026-10-02 追加。** §2 把写入端点定成时间线评论之后，一个直接后果暴露了出来：VS Code 的评论线程
渲染的是**评审**评论，而回复是 issue 层的普通评论，两种对象在 Forgejo 上互不相通——所以按下回复并
成功之后，**线程里什么都不会变**。维护者看到的正是"在 VS Code 里没有任何反应"，而回复其实已经出现在
网页端的时间线上了。这一节记录回显这个决定；§2 的写入路径不变。

### 3.1 决定

- **POST 成功后把回复追加到它被写出的那个线程**（`replyToComment` 的成功分支）。正文**就是刚发出去
  的那份正文**（含引用块）：不做硬换行改写、不解析附件，因为回显里没有哪怕一个字节来自服务端。
- **标记成本地回显**，谁都不要把它当成服务端的评审评论：`Comment.label` 写一句本地化提示（英文
  `Posted to the pull request timeline`，中文「已发布到该 Pull Request 的时间线」，
  `packages/forgejo-toolkit/l10n/` 两份 bundle 同时具备），`Comment.contextValue` 用
  `forgejo-timeline-reply:` 前缀（`ECHOED_REPLY_CONTEXT_VALUE_PREFIX`）。这个前缀刻意**不是**服务端
  评论的 `forgejo:` 前缀：`comments/comment/context` 菜单按 `comment =~ /^forgejo:/` 提供 Delete，而
  回显后面没有任何服务端对象可删，所以它不能拿到这个动作。`CommentMode.Preview` 保证它只读。
- **按线程键记住，重建或重渲染时重新贴回**：回显存进 `EchoedReplyStore`，键就是
  `pullReviewThreadKey` 算出的那个键。线程的 `contextValue` 只带锚点、不带 ref，所以键由线程自己的
  文档 URI（query 里有 ref）加锚点重算——和 `_renderThreads` 用的是同一个函数，是**同一个键**。于是
  刷新、关掉再打开、以及任何一次线程重建，都会把回显作为"服务端评论之后追加的那几条"重新贴回。
  既不会丢，也不会重复：每次渲染都是**重新构造** `rendered + echoes` 并整体赋值，而不是往旧线程上
  再追加一次。
- **不是服务端对象**：回显不进 `_commentContextMap` / `_commentQuoteSources`，不参与删除、不会被
  计数、不会再发一次，也不改变线程对服务端评论的任何判断。唯一需要额外处理的是它带 `contextValue`
  这件事——`replyToComment` 找"被回答的那条评论"时必须跳过回显（`isEchoedReply`），否则第二次回复
  会引用我们自己的本地副本。
- **失败什么都不加**：POST 失败仍然只弹错误、不重渲染、不留任何看起来发出去了的评论（§2.2），
  也就不会有回显被记住。

### 3.2 诚实的限制：回显只活一次会话

回显只存在内存里，**窗口重载后就没了**。线程是从评审数据重建的，而回复永远不在评审数据里；重载之后
线程不再显示它，而回复本身仍在 PR 的时间线上（网页端、本扩展的 PR 详情页），这正是线程自己的提示语和
`KNOWN_ISSUES.md` / `KNOWN_ISSUES.zh.md` 那条所指的地方。

这条限制与"回复不是评审评论"是同一件事的两面：要让回显在服务端持久存在，唯一的路是把它写进某个服务端
对象，而那只有两个选项——写进待提交评审（本次修正否掉的方案，§2.3），或者在服务端再发一条评审评论
（那就是把同一条回复发两遍，而且服务端会多出一条用户没写过的评论）。两个选项都比"本地回显、重载即失"
更糟，所以限制被接受并写进两份已知问题。
