## 1. 问题

通知列表今天只能告诉你"哪一条通知来了"：一行标题、类型图标、未读数，动作是「标为已读」与
「打开」。要判断"这条通知要不要我现在理它"，读者得打开该 issue / PR，把整条时间线从头读到尾——
而讨论可能已经几十上百条。**摘要要回答的是"这场讨论讲了什么、落到哪一步了"**，而不是替读者
决定任何事：它只呈现一段文字，不评论、不回复、不改状态。

它比既有两个 AI 功能**更容易被误点**（它在列表里、每条通知旁边），所以同意面必须比它们更直白：
发出去的是**别人写的正文**，不是读者自己的代码或草稿（§5）。

## 3. 决定一：时间线按「首尾两段」裁剪（2026-10-06）

**决定**：提示词里放**首条正文 + 最早的若干条评论 + 最近的若干条评论**，中间被丢弃的部分在提示词
里写明"中间另有 N 条未包含"。预算怎么分、单条多长、引用块怎么办，见 §3.3。

### 3.1 为什么

- 通知的典型状态是"我可能还没读过这场讨论"：读者要的是**开头（在争什么）与落点（最后怎么定）**，
  所以摘要必须同时看见两端。
- 只留最近的若干条会把摘要变成"结尾"：一条 200 条评论的讨论只喂最后 20 条，摘要的是"结尾"而不是
  "这场讨论"，读者最容易误判。
- 只从头留到预算耗尽，是本仓库对 **diff 与文件正文**的既有纪律（`PR_REVIEW_DIFF_BUDGET` 与
  `AI_PRE_REVIEW_FILE_CONTENT_BUDGET` 都这样做），对代码材料是对的（后面是重复的上下文），但对
  **一场讨论**恰好反了：决定与结论总在尾部。沿用单向的"保留开头"等于把一个为代码材料设计的纪律
  套到对话材料上。
- 代价只有两处边界与一句"中间略过 N 条"，而"每一处截断都在提示词里写明"本来就是既有口径
  （`ai-model-transport.md` §7.2），机制不用新造。

### 3.2 否掉了什么

- **只留最近 N 条**：系统性丢掉问题陈述；而且一旦首条正文可能不进提示词，**同意问句就不能再承诺
  "模型会看到这帖在讲什么"**，摘要的定位要改成"最近发生了什么"——那是内容定位的改变，不只是顺序的
  改变，§5 的 `body-only` 档也随之失去意义。
- **最早优先（填满即停）**：与既有素材的纪律完全一致、代码更少，但对讨论系统性丢结论；选它就等于
  接受"摘要可能不含这场讨论的结论"。
- **首条正文也进预算竞争**：超长首帖会让两种单向策略都退化成"只留最近"，上面两条代价同样适用。

### 3.3 随决定一起定下的细则

- **取哪些条目**：① 首条正文（issue/PR 的描述）；② 评论正文；③ 时间线**事件行**（标签、指派、
  状态变化、评审结论、合并、引用等）——事件**只作一行元数据**（谁、做了什么、什么时候），不是正文。
  评审评论与普通评论同样对待（今天的接口都把它们放在同一份时间线里）。
- **顺序**：整体按时间正序渲染（读者与模型都按发生顺序理解）；截断按「首尾两段」做。
- **单条上限**：一段正文进提示词最多 `PR_REVIEW_MAX_COMMENT_LENGTH` 个字符，**复用既有常量**——
  它的含义是"一段用户写的正文最多多少字符"，本功能与预评审简报说的是同一件事，两个功能不该对
  同一件事有两种答案（与 `ai-pr-description.md` 复用 `AI_PRE_REVIEW_MAX_CONTENT_FILES` 的理由同源）。
- **总预算与首尾分配**：**新常量** `NOTIFICATION_SUMMARY_TIMELINE_BUDGET`，量的是"一场讨论"，
  与 `PR_REVIEW_COMMENT_BUDGET`（一场评审简报的评论）不是同一种材料，且首尾要分成两个子预算——
  硬套旧常量会让"首段给多少、尾段给多少"变成隐式。分配顺序：首条正文（受单条上限）→ 事件行
  （通常极短）→ 评论预算**首尾各半**（各 `budget / 2`）；**一侧用不完的余量让给另一侧**，让余本身
  也写进提示词（否则同一份时间线在不同长度下会得到不同的分配故事）。
- **引用块**：**去掉评论正文里行首的 `> ` 引用块**（连同其后的空行），并在提示词里把它算作一处已声明
  的裁剪。**不做**按文本比对去重：引文可能引用窗口之外的第三方内容，模糊比对会误删；直接去掉
  行首引用块既安全又省下重复的段落预算。
- **逐处截断都写明**（既有口径，`ai-model-transport.md` §7.2）：单条被截、首尾之间被略过 N 条、事件
  行被截、引用块被去掉——每一处都在提示词里出现，否则模型会把局部当整体。
- **确定性**：同一份时间线必须渲染出同一份提示词（纯函数，无隐藏状态），否则 §9 的测试无从谈起。

### 3.4 什么会让我们重新考虑

- 若实测发现结论经常落在长讨论的**腰部**而不是尾部（首尾两段都够不着），取法要改成三段，或改成
  "首条 + 尾部 + 被引用的那几条"。
- 若 `NOTIFICATION_SUMMARY_TIMELINE_BUDGET` 在实践中总是只够首尾各两三条，先调预算，再谈取法。

## 4. 决定二：摘要呈现在**编辑器区标签页面板**（2026-10-06）

**决定**：点动作后开一个编辑器区标签页（照 `AiPreReviewPanel` 的先例，`createWebviewPanel` +
`retainContextWhenHidden`），**同一个面板按当时选中的那条通知重渲染，不叠多个**。面板头部**必须**
显示三样：回答的**模型**、**本次实际使用的范围档**、**这次有没有被截断**。

### 4.1 为什么

- **宽度**：通知列表住在侧栏，实测约 233–297 px（`webview/src/views/settingsGroups.ts` 的注释里
  那次量测），散文在这个宽度里每行只十来个字，扫读成本反而高于打开一个面板；面板能用正常的阅读宽度。
- **只读文本需要的能力**：可选择、可复制、可重新生成一次——三者在树行内联块里都要另造。
- **有先例，且先例已经解决过同样的问题**：AI 预评审的确认面板就是一个编辑器标签页面板，它证明了
  "AI 的输出给一个自己的面"这条路的形状；本功能比它更简单（没有勾选、没有落草稿）。
- **元数据必须可见**：读者要知道"这段是谁生成的、用的哪个模型与哪一档范围、有没有被截断"——面板
  头部正是放这三样的地方；一条消息放不下，也不可回看。

### 4.2 否掉了什么

- **列表内联展开**：会改变行高与树行的键盘/焦点行为（本仓库已经为树行的键盘激活付过
  `utils/treeRowActivation.ts` 这笔钱，见 `KNOWN_ISSUES.md` 的 `<vscode-tree>` 条目），而收益只是
  "少开一个标签页"。
- **实体详情页里的只读区块**：摘要会变成"按实体"而不是"按通知"，得先回答"哪一次摘要、谁触发的、
  缓存放哪、什么时候失效"。
- **VS Code 通知 / 消息**：瞬时、不可复制、不可回看，而摘要的价值之一正是"过一会儿还能再看一眼"；
  它的长度也有限。

### 4.3 什么会让我们重新考虑

- 若实测里读者几乎总是"看一眼就关"，内联展开（或把摘要放进通知行的 `description` 槽）会更省事——
  那时要连带补树行的可访问性路径。
- 若面板日后要同时服务多条通知（例如"按实例汇总"），头部三样与"同一个面板重渲染、不叠多个"这两条
  约束要一起重新裁。

## 5. 同意模型（沿用既有纪律）

- **档位集合与命名**（三个取值加 `ask`，默认 `ask`）：
  - `ask`：**还没回答**。第一次运行时弹**一次**模态框；回答写进全局设置，以后不再问。
  - `body-only`：只发**首条正文**与骨架（仓库 owner/repo、类型、标题、编号、状态、更新时间），
    不发任何评论。适合"我只想知道这帖在讲什么"。
  - `body-and-comments`（模态框**推荐**它）：再加评论正文。它是能"总结一场讨论"的最小档，
    所以是推荐档——推荐不是"最多"，而是"够用且刚好"。
  - `body-comments-and-events`：再加时间线事件行的元数据。
- **逐档说清发什么**：模态框对每一档分别写出"会发出什么"（骨架 / 首条正文 / 评论正文 / 事件元数据），
  并点名目的地（编辑器提供的模型点 vendor；自配端点写显示名与地址），照 `ai-model-transport.md` §7.1
  的句式。
- **明确不发**：访问令牌、实例地址或主机名、`subject.url` / `html_url` 这类**字段**、参与者邮箱。
  **但正文里作者自己写下的链接与名字随正文原样**——它们是作者的内容，不是我们附加的字段；
  把正文"清洗"成不带链接的版本会改变材料本身，那是另一件事（§8 记为不做）。
- **`ask` 是 fail-closed**：没回答就不读时间线、不取模型答案、不发任何请求（零读取、零请求、零写入），
  运行以 `cancelled` 结束，面板只说明"还没选范围"。取消也走同一条路。
- **顺序澄清（2026-10-07，实现时发现与 §7.3 的次序冲突后由维护者裁决）**：**取模型在模态框之前**，
  按 `ai-model-transport.md` §7.3 与已交付的两个 AI 功能同序——模态框必须点名目的地，而 §7.1 的句式
  需要 vendor（编辑器模型）或自配端点的显示名与地址。fail-closed 保住的正是要紧的那半：**回答之前
  不读时间线、不发任何网络请求、不做任何模型补全、不写任何设置**；`selectedModelFor` 本身是本地解析
  （读设置与端点清单），不构成出网。也就是说，这里的"零"是**读取、请求与写入**为零，不是"连模型都
  不许解析"。§5 的三档取值、fail-closed 的决定与 §7.1 的句式都未因此改变。
- **「配置好了」不等于「同意出网」**（`ai-model-transport.md` §7.3）：AI 总开关开着、端点配好、
  本功能开关也开着，都只是"可以问"，不改变这里要问一次。

## 7. 失败与降级

- **模型不可用**（`selectedModelFor` 回 `unavailable`）：一句提示并指向设置页，零请求、零模型调用。
- **无权限 / 端点拒绝**：按名失败（点名模型或端点），不换路、不换模型、不自动重试。
- **端点截断**（`finish_reason: 'length'`）：走既有的 `truncated` 报告，**面板头部与正文都明说这段
  摘要可能不完整**，不假装完整。
- **截断的两种原因必须分开说（2026-10-07，实机走查发现的问题）**：原先把两件事合并成了一句，于是
  "回答完整、只是材料被裁过"也被说成"这段摘要可能不完整"——**把话说重了**。两个原因不同，说法也必须
  不同：
  - **`answer`**：端点自己停在输出上限（`finish_reason: 'length'`）⇒ 不完整的是**摘要本身**；
  - **`material`**：提示词里的材料被裁过（去掉的行首引用块，或首尾之间略过的条目）⇒ 模型只看到这场
    讨论的一部分，而摘要**对它所看到的部分是忠实的**；该说的是"模型看到的是裁剪过的讨论"，而不是
    "摘要可能不完整"；
  - 两者同时发生即 `material-and-answer`，两句都要说。
    载荷因此带 `truncationReason?: 'material' | 'answer' | 'material-and-answer'`（缺失即"没有截断"），
    面板头部的那个值与正文那句都据此选词。这是对报告口径的细化，不改 §3/§4 的两项决定，也不改 §5 的
    档位与 fail-closed 结论。
- **时间线为空**（或所选档位下没有任何可发正文）：**不调模型**，面板直接说「没有可摘要的讨论」。
- **摘要过长**：**拒绝**并说明，而不是截断后当摘要用（`ai-pr-description.md` §6 的同一条口径）。
- **时间线读取失败**：一句失败，零模型调用。
- 以上任何一条都不产生服务端写入。

## 8. 明确不做

- **不在轮询里自动摘要**：只在用户按下动作时运行。后台为每条未读通知预生成摘要既费额度，又把
  "别人写的正文"在用户没有动作时送出去。
- **不摘要 repository / commit / release 等其它通知类型**：动作只出现在 issue / pull 类型的通知上
  （今天 `Notifications.vue` 的 `typeFilter` 已经区分这几类）。**这条约束是关于"类型"的，不是关于"面"的**：
  同一个动作也可以从该实体的**详情页**发起（2026-10-07 扩展，见 §10），那仍然是"对一个 issue / PR 的
  讨论"的摘要，没有放宽到别的类型。**仪表板/仓库页的列表行**（第三个面）仍不在范围内，随上下文菜单的
  清单一起推迟。
- **不向服务端写任何内容**：不评论、不回复、不改状态、不把"已读"当成摘要的副作用。
- **不做正文清洗**：不改写、不删链接、不匿名化正文（§5 说明了为什么"不发 URL 字段"不等于"清洗正文"）。
- **不新增 API 端点**：材料用既有的 `/issues/{index}/timeline`。
- **不做"一键摘要全部未读"**：一次一条通知。

- **裁剪器（纯函数）**：条数与字符预算、§3.3 的首尾各半分配（含一侧用不完时的让余，以及让余也写进
  提示词）、单条截断、引用块被去掉、事件行格式、"中间略过 N 条"写进提示词、同一输入得到逐字节

  时间线为空时不发生模型调用；过长回答被拒绝而不是被截断。
- **页面**：动作在**两个面上**都出现——通知列表的行，以及 issue / PR 的详情页——而**两个面都只对
  issue / pull 实体**提供：repository / commit / release 在任一面都不出现这个动作。面板头部的三样
