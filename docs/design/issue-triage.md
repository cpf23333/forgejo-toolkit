# Issue 标签建议（labels，逐条确认后经既有编辑弹窗应用）

- 状态：**设计已定稿；已交付**（2026-10-06）。本记录只写今天成立的决定与理由，以及决定当时否掉了什么。

- 适用范围：Issue 详情页上的一个动作——让模型按该 Issue 的内容，从**这个仓库已有的标签**里挑出建议；用户逐条勾选后，
  扩展打开**既有的编辑表单**并预填勾中的标签，由用户自己保存。**只建议标签**：本功能不读、不发、也不建议任何
  负责人（收窄的理由见 §2）；不含任何自动应用、不含对 Issue 列表的批量分诊、不含 webview 里的任何模型调用
  （`vscode.lm` 只在扩展宿主可用）。

- 关联：模型接缝、传输选择、外发同意与能力降级的总记录是
  [`ai-model-transport.md`](./ai-model-transport.md)——本记录只落**本功能特有**的决定，接缝的形状（§4）、两条传输
  不得互相回退（§7.5）、设置与密钥面（§8）、能力判断与降级（§9）都在那里定稿，本文不再重复。设置面在页面上的
  呈现见 [`settings-page.md`](./settings-page.md) §1.3 与 §3.2。

- 定稿日期：2026-10-06（接缝与另外两个功能落地之后，本功能是第三个接上 `selectedModelFor(feature)` 的功能）。

## 1. 问题

`TODO.md` 的那一条写的是「按内容建议 labels/assignees（把现有 label 描述喂给模型选）」。落地要回答的问题有四个，
都不是「怎么调模型」：

1. **新的外发内容类别**：要建议标签，就得把**仓库自己的标签清单**（名字与描述）发给模型；这在预评审与 PR 描述
   生成里都没有先例（那两个功能发的是被审对象的材料，不是一个仓库的元数据）。它是一次新的出网决定，必须有
   自己的一次同意，而且同意句要把它点名。
2. **建议必须落在真实对象上**：模型可以写出任意字符串，而"标签"是一个**这个仓库有没有**的事实。落不上的建议
   不能靠模糊匹配救回来——写错一个标签就是对 Issue 的一次公开写入。
3. **扩展不能替用户写**：Issue 的标签是**立即公开**的改动，没有预评审那套"待提交评审"可以暂存。所以这个功能的
   产品只能是**建议**，应用必须走用户自己的保存。
4. **仓库没有标签时怎么办**：一个没有任何标签的仓库，"建议标签"这句话没有可落地的对象。**决定：那时这个动作
   根本不出现**（§3.2），运行侧另有一道兜底（§6）。

### 1.1 收窄：不再建议负责人

本功能最初同时建议**负责人**，候选来自仓库的可指派 login 清单。**维护者裁决把它整条去掉**，理由是：可指派 login
清单本身是一份新的外发内容，而模型唯一能依据的线索是**评论里出现过谁**——据此把"谁该负责这个 Issue"告诉读者，不是
一个足够好的依据。这样收窄之后：

- `[assignees]` 段与那份 login 清单**不再读取、不再发送**（同意句也不再承诺它，见 §4）；
- 回答契约只剩 `labels` 一个键（§5）；
- 与负责人有关的丢弃原因与上限一并删除；
- 面板与"应用"路径**完全不碰负责人字段**（§7）。

标签那一侧一个字都不放松：精确匹配、按原因计数、无标签时直说、两个档位。

## 2. 材料：读什么、不读什么

| 读（`issue-only` 档的底线）                                        | 不读 / 不发                                                             |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| 该 Issue 的**标题与正文**                                          | 该 Issue **当前已有的标签**（另有来源，且同意句没承诺发它）             |
| 仓库的**标签清单**：每个标签的名字与描述，`is_archived` 为真的排除 | **可指派的用户 login 清单**（收窄后不再读；理由见 §1.1）                |
| `issue-and-comments` 档再加：**讨论评论**（正文 + 作者 + 时间）    | 访问令牌、URL / 主机名（沿用 `ai-prereview.md` §7.1 的底线）            |
|                                                                    | Issue 的作者、时间、附件、订阅者等详情字段；仓库里的任何文件、任何 diff |

- **为什么标签清单是底线的一部分**：没有它，模型只能凭空编标签名，而每个名字后面都必须有真实 id 才能落地。把
  **候选集合**发出去，是让"建议"这个词有意义的前提（也正因为它是一次新的外发内容，§4 的同意句必须点名它）。
- **归档标签被排除**：Forgejo 保留它们给既有的 Issue，但不再提供给新的选择；建议一个用户选不到的标签，等于
  建议一个无法完成的操作。缺 id 或缺名字的条目同样排除（没有 id 就无从应用），两处排除都**计数并写日志**。
  这条塑形规则只有一处实现（`suggestableLabels`），运行与 §3.2 的可用性判断共用它。
- **讨论只在该档位读**：`issue-only` 下运行**根本不发那次时间线请求**，所以"评论不会进提示词"不是提示词里的
  一句承诺，而是构造上成立。哪些行算评论（有正文的时间线行）在 `timelineComments` 一处定义。
- **顺序与上限**：标题截到 `ISSUE_TRIAGE_MAX_TITLE_CHARACTERS`（300）、正文截到
  `ISSUE_TRIAGE_ISSUE_BODY_BUDGET`（= 预评审的 `PR_REVIEW_COMMENT_BUDGET`，24 KiB）；标签表受
  `ISSUE_TRIAGE_MAX_TABLE_ROWS`（= `PR_REVIEW_MAX_DIFF_FILES`，100 行）与 `ISSUE_TRIAGE_TABLE_BUDGET`
  （= `PR_REVIEW_DIFF_BUDGET`，16 KiB）约束；讨论最多 `ISSUE_TRIAGE_MAX_COMMENTS`（= `PR_REVIEW_MAX_COMMENTS`，50）
  条、整段受 `ISSUE_TRIAGE_COMMENT_BUDGET`（= `PR_REVIEW_COMMENT_BUDGET`）约束、单条正文截到
  `ISSUE_TRIAGE_MAX_COMMENT_CHARACTERS`（= `PR_REVIEW_MAX_COMMENT_LENGTH`）。**每一处截断都写进提示词本身**，
  否则模型会把局部当整体。

## 3. 设置与范围

| 设置                                    | 取值                                        | 默认    | `scope`   | 语义                                                       |
| --------------------------------------- | ------------------------------------------- | ------- | --------- | ---------------------------------------------------------- |
| `forgejoToolkit.issueTriage`            | boolean                                     | `false` | `machine` | 本功能是否可用；关闭时控件不显示、不读 Issue、不发任何内容 |
| `forgejoToolkit.issueTriagePromptScope` | `ask` / `issue-only` / `issue-and-comments` | `ask`   | `machine` | 提示词可以携带什么；`ask` 是**问题**而不是答案             |

- **第三个功能自己的两个设置**：不复用预评审的五个取值、也不复用 PR 描述生成的四个。三者发送的字节各不相同
  （这里多了**标签清单**这一类），"一个值只能有一个含义"是硬要求。
- **`machine` 作用域**：两个设置都声明为 `machine`，所以工作区级的 `.vscode/settings.json` **不能**替用户打开这个
  功能、也不能把它的出网范围放宽到讨论。逐功能开关按 `machine` 声明，正是 `ai-model-transport.md` §8.3 对端点设置
  用的那条论证落在**出网范围**上：一个仓库可以带一份把 Issue 正文与讨论送出去的配置，而用户从未同意过。
  本功能落地时 `aiPreReview` / `prDescription` 及其范围还是 `window` 作用域，那一处不一致当时只记录、没有顺手改；
  **同一天维护者就同一理由裁决把它们一并收进 `machine` 一族**，连预评审记住的模型 `aiPreReviewModel` 也在内——
  那个键的理由最直接：它不是"发多少"而是"**发给谁**"，一个工作区级的值足以把内容改道到另一个 provider（裁决全文见
  `docs/design/ai-model-transport.md` §8.3 的「第二处作用域裁决」与 `settings-page.md` §3.5；那一族今天共 14 个键），
  所以三个功能今天在同一条纪律上：这些键上的工作区级值不再生效。
- **`ask` 的读法照旧**：非字符串 / 读不到 / 拼错一律读作 `ask`（fail-closed 的方向是"什么都不发"），只有显式取值
  才算答案；回答写回**全局**设置，所以问题只问一次。

### 3.1 哪一档在哪一面兑现

**决定：本次运行所在的表面能服务哪些档位，是代码里的一条事实；配着这一面兑现不了的档位时，运行按名拒绝、不换档、
不重问。**

- `issueTriageScopesForSurface('issue-detail')` 今天返回 `['issue-only', 'issue-and-comments']`：讨论就是对同一个
  页面的一次读取，所以两个档位都能兑现。这个函数是同意模态框与运行**共读**的那份事实——模态框只提供它返回的
  答案（另加取消），运行则对声明在设置里的、不在其中的档位按名拒绝。
- **不换档**是硬纪律：换档就是发出用户没选过的字节。**重新提问**也不行：`ask` 是设置里"还没回答"的拼法，不是
  "这个答案放不下"的退路，重问会覆盖用户已经给出的回答。
- 今天这个分支从界面上不可达（唯一表面能服务两档）。它是**接缝上的一道闸**：表面若多一个（或档位若多一个）而
  能力表没跟上，运行会按名失败而不是悄悄少发内容。

### 3.2 仓库没有标签时不显示这个动作

**决定：一个没有声明任何标签的仓库，不提供这个动作。** 那时它没有任何可建议的东西，显示一个按下去只会得到运行
自己的拒绝的控件，是让读者为一个必然的失败付一次点击。

- **宿主来学这件事**，因为答案是关于**仓库**而不是关于 Issue 的，页面在知道打开的是哪个 Issue 之前读不到标签清单。
  页面请求 Issue 详情时，宿主在详情回复之后**读一次该仓库的标签清单**，把"有没有可建议的标签"记在这个 provider 的
  一张按 `instanceId|owner|repo` 索引的表里，再用既有的 `setIssueTriage` 消息把它推给页面（与功能开关同一条消息：
  这是关于同一个控件的同一个事实）。同一窗口里第二次打开同一仓库的 Issue 直接命中缓存。
- **成本**：每次打开一个**尚未读过**的仓库的 Issue 详情**多一次 `/labels` 读取**；同一仓库的后续 Issue、
  以及重新打开同一个 Issue，都是 0 次（缓存命中）。**这不是出网**：它是一次普通的 API 读取，答案从不发给任何
  模型提供者，而且只在功能开关打开时才读。缓存不落盘，宿主随窗口结束而消失——标签清单会变，一个跨会话的缓存
  会拿着旧答案。
- **未知答案按"有标签"处理**：宿主还没读到之前（初始状态、读取失败、或刚在设置里打开开关），页面**继续提供**
  这个动作——"读不到"不是"没有"的证据。读取失败**不缓存**，所以下一次打开会重试。
- **运行侧另有一道兜底**（与页面无关）：运行读到空标签清单时**按名拒绝**，零请求、零模型调用（§6）。所以过期的
  界面最坏只会被拒绝，而不会把一个空候选集发给模型。
- **判据与测试**：宿主的读取用 `suggestableLabels` 判断，与运行用的**同一条塑形规则**，所以"页面隐藏"与"运行拒绝"
  不可能对"什么算一个标签"产生分歧；mock API 里有一个**故意没有标签**的仓库（`MOCK_LABEL_FREE_REPO`），让这条规则
  在真机走查里可达，而不是只在单元测试里成立。

## 4. 同意

**决定：本功能有自己的功能开关与自己的提示词范围，两者默认关闭 / 默认是问题；同意模态框只问一次，答案写回全局设置。**

- 模态框写四件事，与其他功能一样：目的地（编辑器自己的模型点名 vendor；自配端点写**显示名与地址**）、每个答案
  分别会发出什么、答案被写回哪个设置、以及"在你回答之前不请求、不发送也不读取"。
- **两个答案各自的样子**（`issueTriagePromptScopeMessage`）：
  - `issue-only`：该 Issue 的**标题与正文**、仓库的**标签清单**（每个标签的名字与描述，已归档标签不算在内）——
    **不含任何讨论评论**，所以模型看到的是 Issue 写下的内容，而不是别人已经说过的。
  - `issue-and-comments`：在上面基础上**再加上讨论评论及其作者与时间**——这是内容最多的答案，也是模型唯一能把
    已有讨论考虑进去的答案。
  - 两个答案都**不发**访问令牌、URL 或主机名。
- **收窄之后句子也要收窄**：它只承诺 Issue 的正文与标签清单，**不再提可指派的用户清单**（§1.1）——一句承诺了
  不再发送的内容的同意句，是一句假话。
- **读取在回答之后**：功能开关 → 表面与档位是否匹配 → 取模型 → **这一次同意** → 才读材料。范围仍是 `ask` 时，
  运行的第一个动作就是那个模态框；取消则零读取、零请求、零写入。
- **没有"同一设置、两种答案集"的坑**：这个功能只有一面，两个答案在那一面都兑现得了，所以不存在"在 A 面答过、
  到 B 面就看不到某个答案"的情况（PR 描述生成那边有这个坑，记在 `ai-pr-description.md` §3.1）。

## 5. 回答校验：建议必须落在真实对象上

**决定：模型回答一个 JSON 对象 `{"labels": [...]}`；这个键必须存在（"没有可建议的"写作 `[]`），每一条都在
**同一次运行读到的候选集合**里**精确相等**地解析；解析不了的**丢弃并计数**，绝不模糊匹配。**

- 契约的三个失败彼此分开：**空回答**、**不是 JSON**（散文或未闭合的围栏）、**形状不对**（`root` 或 `labels`）。
  一个 JSON 代码围栏允许被剥掉（那是模型经常犯的序列化错误，不是内容修复）；散文围在 JSON 外面仍然算失败。
- **只认 `labels`**：回答里出现 `assignees` 之类别的键不影响解析（它们被忽略），但 `labels` 不是数组就是形状失败——
  这个功能没有第二个可建议的对象（§1.1）。
- **精确相等**：标签名按 `trim` 后的逐字比较。`"Bug"` 与 `"bug"` 是两个字符串，不做大小写折叠、不做前缀匹配、
  不找"最像的那个"——应用标签是对 Issue 的一次公开写入。
- **计数**按原因归类（`invalid-shape` / `label-not-in-repository` / `over-limit`），面板逐原因显示条数。
  **重复项折叠但不计数**：同一个标签说两遍是同一个建议，不是一次拒绝。
- **上限在解析之前应用**：最多 `ISSUE_TRIAGE_MAX_LABEL_SUGGESTIONS`（5）条，超出的按 `over-limit` 计数——它们
  **从未被考虑过**，这与"名字落不上"是两件不同的事。
- **仓库没有标签时运行根本不会走到这里**：它先按名拒绝（§3.2、§6）。校验器仍然会把任何标签建议按
  `label-not-in-repository` 丢掉，因为一个手工构造的 brief 不该表现得像"可以编一个标签"。

## 6. 失败与降级

- **顺序即降级面**：`aiEnabled`（由 `selectedModelFor` 在任何分支之前回答）→ 本功能开关 → 表面/档位匹配 →
  取模型 → 一次同意 → 读取 → 预算 → 一次请求。
- 失败一律**说清楚**，且只对**那一个**模型说一次：读 Issue 失败、读仓库标签失败、读讨论失败各自一句；模型调用
  失败、被拒绝授权（`NoPermissions`）、回答契约不成立各一句。**不换模型、不换传输、不自动重试**。
- **仓库没有标签**：一句"这个仓库没有声明任何标签，所以没有可建议的内容。没有向模型发出任何内容。"，零请求、
  零模型调用（§3.2 的兜底；正常路径下这个动作根本不显示）。
- **没有可用模型**时只报一句并指向**设置页**（`ai-model-transport.md` §9.3），零请求、零模型调用。
- **预算**：先量指令提示词（决定预算口径），再量**这次要发的整段文本**；装不下就报两个数字并拒绝，**不截断提示词
  后照发**。
  - **量什么就必须发什么，系统指令在线上只出现一次**（2026-10-06 的修复）：接缝请求把指令块与材料**分开**交给
    传输，怎么拼是传输自己的事（OpenAI 兼容那条把 `system` 作为单独一条消息发，编辑器那条把它前置到唯一一条
    user 消息上）。把拼好的整段当作 user 消息再交给一个"会把 `system` 也拼进去"的构造器，会让指令在线上出现
    两次，而预算只按一份量——落在两个数字之间的模型会通过一个它装不下的检查。回归测试钉住的是**实际发出的文本**
    （指令块只出现一次，且量到的文本等于传输渲染出来的那段），不是构造器的中间值。
- **端点截断**要说出来：`finish_reason: 'length'` 时，契约失败的句子后面追加端点自己那句；答案解析成功但端点
  自报截断时，面板也显示一行——一份被截断的短建议列表不该看起来像"模型只想到这些"。
- **取消**：用户取消同意或模型选择器 → `cancelled`（不是错误，宿主已经就地说明过）；运行中的取消走同一个可取消
  进度通知（`withProgress({ cancellable: true })` + `abortSignalForToken`），产物只是文本，没有要回滚的东西。

## 7. 交出去的表面

- **控件**：Issue 详情页头部动作区里，「建议标签」按钮（与 PR 详情页的 AI 预评审按钮同形）。它出现的条件是
  **宿主报告开关为开**、**宿主报告这个仓库有可建议的标签**（§3.2），并且这一页能管理这个 Issue（作者本人、
  或有 push/admin 权限）——因为唯一的应用路径是那张编辑表单，用一个没有保存按钮的入口去"应用"建议没有意义。
  按钮的显示与否**只是有没有这个入口**：运行自己会重读设置与标签清单，并按自己的话拒绝。
- **建议面板**：逐条列出建议（标签带名字与颜色），**默认一条都不勾选**；头部写明本次范围与是哪个模型答的；被丢弃的
  建议按原因显示条数；一条都没建议时说出来；端点自报截断时显示那一行。面板是纯显示件：里面每一个 id 都是宿主
  在那次运行里解析出来的，页面无从编造。
- **应用路径**：勾选后按「在编辑表单里应用」→ 打开**既有的**编辑表单，把勾中的 id **预填**进它的标签选择器
  （与 Issue 现有的标签取并集）；用户按保存，走的是与手动编辑完全相同的 `editIssue`。**扩展自己从不写任何东西**：
  面板里的"应用"只是打开一张表单，而**负责人字段完全不被触碰**（不预填、不改写、不提示）。
- **没有命令**：这个动作需要一个具体的 Issue，而只有页面知道当前打开的是哪一个（另外两个功能的命令是为了让一个
  能从 diff 文档或表单里自己解析目标的能力在命令面板里有名字）。所以本功能只注册消息处理器，不贡献命令。

## 9. 否掉了什么

- **建议负责人**（收窄，§1.1）：候选只有一份可指派 login 清单，而模型唯一能依据的线索是评论里出现过谁；据此告诉
  读者"谁该负责"不是足够好的依据。整条删除，而不是保留一个"仅供参考"的弱化版本。
- **自动应用任何建议**：标签是立即公开的改动，没有暂存态；应用只能是用户自己的保存（§7）。
- **整列表批量分诊**：一次运行针对一个 Issue；批量会让"逐条确认"这件事失去意义，也让每个 Issue 的材料变成一次
  大规模出网。
- **为分诊新增 MCP 写工具**：那是另一个面（agent 的写权限有自己的确认模型），本功能不碰写侧。
- **模糊或近似匹配标签名**：见 §5，错标签是公开写入。
- **把"建议"做成自由文本**（让模型随便描述该打什么标签）：那样没有可落地的 id，用户还得自己翻译一遍，反而更容易
  打错。
- **没有标签时"显示但禁用"**：一个禁用按钮说明不了"为什么"，而这句话（这个仓库没有标签）属于**页面本来就该知道
  的事实**，不是一次运行的失败；所以是隐藏 + 运行兜底，而不是一个按不动的控件（§3.2）。
- **为"有没有标签"另开一条消息**：它与功能开关说的是同一个控件的同一个事实，多一条消息只是多一个可以漂移的
  状态（§3.2）。
- **复用预评审或 PR 描述生成的提示词范围**：三者发送的字节不同，同一个值指向不同字节就是"一个值两个含义"。
- **顺手把 `aiPreReview` / `prDescription` 的范围也改成 `machine`**：本批落地时**否决**了顺手改它们（那是既有的一处
  不一致，改它要连同两条已交付设置的迁移与文案一起决定）。**同日维护者就同一理由单独裁决了这件事**，所以它不再是
  "否掉的"而是已交付的一项：结论与行为变化记在 `docs/design/ai-model-transport.md` §8.3 的「第二处作用域裁决」，
  本节 §3 的第一条也改成了今天的现状。
- **一个命令面板入口**：这个动作需要一个具体 Issue（§7）。
- **失败后自动改用另一条传输 / 另一个模型**：`ai-model-transport.md` §7.5，硬要求。
- **过长的回答截断后照用**：契约失败就是失败（§5、§6）。
