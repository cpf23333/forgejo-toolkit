## 1. 页面与 VS Code 设置的分工

### 1.1 判据一句话

**页面只承载原生设置界面表达不好的东西，以及一个区块要能用就必须有的东西；其余的值留在原生设置界面，它是这些
值的唯一可写来源；页面永远不做第二个可写来源，不自带默认值，也不自带校验。**

三条限制说的是同一件事的三面：

1. **表达不好**的：数组与对象（原生界面只能让用户手编 JSON）、密钥（`SecretStorage`，原生界面里的
   `application` scope 设置也放不下它）、多字段编辑器（一条记录有 id、地址、认证方式、模型、header、密钥六个面，
   原生界面里是六个没有关联的文本框）、以及**需要一个动作**才能回答的（"这个端点通不通"只有发一次请求才知道）。
2. **区块要能用**：一个区块写"AI 端点在这里配置，但要不要用 AI 在别处的一个开关上"，就是把用户送到一个他不
   知道去哪找的地方。判据不是"这个值简不简单"，而是"这个区块的叙述在缺了它之后还成不成立"。
3. **唯一来源**：同一个值有两个可写控件，就必然有两个校验、两个默认值、两个错误出口；用户在一边被拒、在另一边
   被接受时，没有任何办法说出哪一个是权威。本页今天已经踩在这条线上：`worktreeCacheDirectory` 字段自己用
   `applyWorktreeCacheDirectory` 把被宿主拒绝的路径**弹回**原生值，这个动作之所以成立，只是因为它是"读回去"
   而不是"校验一遍"。

### 1.2 这条规则在现有页面上的例外，以及为什么留着

现页已经渲染了五条本可留在原生的设置：`locale`（枚举）、`debug`（布尔）、`worktreeOpenMode`（枚举）、
`worktreeCacheDirectory`（短字符串）、`aiModelRequestTimeoutMs`（带上下限的数字）。它们**不因为这条规则回退到
原生界面**，理由是各自都属于上面第 2 条：

| 现页渲染的                                    | 为什么它属于"区块要能用"                                                                                                          |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `worktreeOpenMode` / `worktreeCacheDirectory` | 工作树区块要讲的是"PR 检出到哪儿、怎么打开"；把这两个值搬到原生界面，这个区块就只剩一个列表，用户无法在同一个地方回答它提出的问题 |
| `aiModelRequestTimeoutMs`                     | 这个数字的意思（**空闲**窗口，超时总量是它的十倍）只写在它的描述里；把它搬走等于把"这个数字到底管什么"拆成两处                    |
| `locale`                                      | 这一条只有一半：语言该在页面里改，因为它要立刻改变**用户正在看的这个面板**，而原生界面改完要等一次重载                            |
| `debug`                                       | 调试日志是页面问题的诊断出口（`Forgejo Toolkit` 输出通道），从页面就近打开比从原生界面找快得多                                    |

结论：本文的规则约束的是**新增**哪些设置上页面，以及**哪些新设置只能留在原生界面**，不是一次对现页的清算。

## 2. 可发现性

### 2.1 一个通往原生设置的入口，且**筛到本扩展**

页头（列表态与两个编辑器态都可见，因为它是页面的属性而不是某个区块的属性）放一个次要控件：
**「打开扩展设置」**。它打开的必须是 `workbench.action.openSettings`，参数 `@ext:cpf23333.forgejo-toolkit`，
即**按扩展 id 筛过**的原生设置界面——不是不带参数的设置界面。理由：不带参数会让用户落在一整片与他无关的设置里，
而这正是本页存在的原因（他找不到"我们这个扩展的设置在哪"）。

**筛选用的是扩展 id，不是包名。** id 是 `<publisher>.<name>`，也就是 manifest 的 `publisher` 与 `name` 拼起来；
`@ext:forgejo-toolkit`（只有包名）谁都匹配不上，编辑器会打开成"没有找到设置"。所以宿主不把这个字符串抄第二遍，
而是用运行中的这个扩展自己的 id（`context.extension.id`）拼出过滤器——真实编辑器走查里正是这个少了 publisher
的过滤器让入口开出了一个空编辑器。

**命令 id 的取舍（本文的裁决）**：宿主已经有 `forgejoToolkit.openSettings`，它的语义是**打开本页**
（`commands/index.ts` 的 `registerCommand('forgejoToolkit.openSettings', () => viewProvider.openSettings())`，webview 侧
`useAppState.ts` 的 `case 'openSettings'` 切到设置视图），而它在命令面板里的标题恰好就是「Open Settings」——一个
与原生「Preferences: Open Settings」几乎重名的入口，会把用户送进本页。所以**不动它**，新增**一个**命令
`forgejoToolkit.openNativeSettings`，标题取自 nls 对（`%command.openNativeSettings.title%`，中英各一份），由宿主以
`@ext:${context.extension.id}` 为参数调用 `workbench.action.openSettings` 实现（id 的来历见上一段）。改旧命令的
语义是另一条路，但会让"打开设置"这个标题指向两个不同的地方，本文否掉。

### 2.2 每个区块的"更多设置"指针

区块里凡是留在原生界面的设置，都在该区块末尾放一行**同一种形状**的指针，而不是在页面里再画一个控件：

> 更多设置：`forgejoToolkit.notificationPollingInterval`（轮询间隔，秒）—— 在 VS Code 设置中打开

这一行由三段组成，且三段都不许省略：**设置 id**（等宽字体）、**一句话它管什么**、**一个动作**（打开原生设置，
用 §2.1 的同一个命令）。指针行是可点的，点它就打开筛好的原生设置；不写 id 而只写"更多设置"是不够的，因为用户
在原生设置里搜索时需要的正是这个 id。

保留在原生界面的两条与它们的落点：

| 留在原生的设置                | 指针落在哪个区块                                  | 一行里必须说清的                               |
| ----------------------------- | ------------------------------------------------- | ---------------------------------------------- |
| `notificationPollingInterval` | 通知区块，`notificationPollingEnabled` 的开关下面 | 单位是**秒**，范围 60–3600                     |
| `useMockApi`                  | **无**                                            | 不提。它是开发开关，提它只会让用户以为这是功能 |

`aiTransport` 曾经在这张表里，2026-10-06 起它是页面自己的控件（§1.3），因此不再有指针行：一个值有两个可写
控件正是 §1.1 第 3 条禁止的，所以它只能是二者之一。

### 2.3 页面里的设置名怎么写

**原生设置用它的 id 指称，页面自己的控件用它的标签指称。** 具体：

- 原生设置一律写成等宽字体的完整 id（`forgejoToolkit.aiTransport`），**不翻译、不简写**成"传输方式"这样的中文
  名；用户要拿着这个字符串去原生设置里搜，翻译过的名字搜不到。id 是标识符，不是界面文案，所以它不进
  `webview/src/i18n/*.json`，而把 id 嵌进去的那句说明走那个语言文件。
- 页面自己的控件用 `en.json` / `zh.json` 里的标签（`settings.worktree.cacheDirectory` 这类），和今天一样。
- 宿主侧文案（如指针行的动作、`showInformationMessage`）走 `l10n/bundle.l10n.*.json`；**manifest 里的设置名与描述**
  走 `package.nls.json` / `package.nls.zh-cn.json`，那是原生设置在两种语言下的样子，不与页面的键混用。

## 3. 呈现方式

### 3.1 复用 AI 端点编辑器立下的四条约定

这四条是现页已经跑通、本文要求其余区块照做的，不是新发明：

1. **一行是"必须行动的事实"，不是一句散文。** `AiTestReport.vue` 的 `dl.test-report-facts`：先"请求发到了哪个
   地址"，再状态码，再耗时，最后才是宿主自己那句话。事实的顺序固定，值不改写、不复述。
2. **被拒绝的条目要**点名**并附上原因。** `settings.aiProviders.rejected` 区块逐条写第几条、id 是什么、为什么读不
   出来——静默消失的条目正是这个页面要防的那种"没法诊断"。
3. **已设置的值显示为"已设置"，不回显。** 密钥与 header 的 value 从不回到 webview：字段是空的，旁边写"已存储一个
   密钥"，清空是它自己的一个控件。
4. **控件跟着宿主，不跟着点击。** 写失败时控件回到宿主报告的值，并在旁边给出错误（`savePolicy` 的处置）；页面
   永远不会显示一个从未被存下的状态。

### 3.2 逐条呈现

控件类型按现有约定选：`vscode-checkbox`（布尔）、`vscode-single-select` + `vscode-option`（枚举）、
`vscode-textfield`（文本 / 数字）、`vscode-button`（动作）。**顺序**按"先能用的前提、再细节"排，且每个区块
内部固定；**默认值**不预填进控件，而是在控件下面用一行说明写清默认是什么（`default` + 它的单位），因为预填会让

是这一页，跟着它一起消失就等于把"重新打开 AI 之后要用的东西"藏进一个用户打不开的地方；而"配置不是使用"，把开关拨回
来本身不需要先配好任何东西。

端点面、`openai-compatible` 下的编辑器模型行），不能是"页面不喜欢"的东西；② 每一处隐藏都必须在它原来的位置留下
一句可读的说明，并且**做出这个选择的控件本身永远可见**——用户要能就地改回来。§3.3 第 3 条的"什么都不隐藏"讲的是
**值**（密钥、header value 从不回显），与这里按选择裁剪**控件**不是同一条规矩。

`aiPreReviewPromptScope` 上页面的理由必须在这一节写死：它是**出网范围**的单一来源，页面不复制它的校验——下拉的
五个取值来自同一个枚举顺序，页面把这个值写回设置，**从不自己纠正**一个页面读不懂的值（那由宿主的读取器按
`ask` 处理，页面只显示宿主报告的值）。

### 3.3 值被拒绝、被忽略时统一怎么写

三种状态各有固定的写法，不许混用：

1. **本地就不合法**（地址不是 URL、id 里有非法字符）：控件下面的说明行写原因，控件本身**不**清空用户输入——
   这与实例编辑器"声明的版本号永远不丢"是同一条规矩。
2. **整个 AI 面被关着**（`aiEnabled` 是 `false`）：在**那个开关自己的行**上写一句"关掉意味着什么、怎么打开"，用
   主题的警告色（`--vscode-editorWarning-foreground`）；**不**禁用开关，也不隐藏它关住的那一片配置。这条替换了
   原来的"被本地策略拒绝"一格（`aiLocalOnly` 已移除，`ai-model-transport.md` 的 §8.8 记了理由）。
3. **被宿主拒绝**（写失败）：控件回到宿主报告的值，旁边给宿主的原句；页面不加自己的解读。

## 4. 改进一：模型列表自动探测

### 4.1 现状与它为什么不够

今天唯一会发请求的动作是每个端点行 / 编辑器上的**「测试连接」**按钮，走 `state.testAiProvider(id)` →
`aiTestProviderReport`。它有两个限制：编辑器里的按钮在 `editingProviderId === null`（新增模式）时是禁用的，
因为探针要按 **id** 找已存下的端点；而密钥必须先把端点写下去才能存（`providerSecrets.ts` 的 key 形状就是
`forgejoToolkit.aiProviderKey.<providerId>`）。于是"填了地址和密钥，看看这个端点有哪些模型"这件事，今天至少要
两步保存。

### 4.2 决定：探测跑的是一份**草稿**，不是已保存的端点

新增一条 webview→宿主的请求，名字落在 `packages/shared/src/webview/messages.ts`（与 `saveAiProvider` /
`testAiProvider` 同一处），形如 `testAiProviderDraft`，载荷是编辑器**当前字段**：`baseUrl`、`auth`、本次输入的
`key`、以及本次输入的 header 名/值对。宿主用它拼一份临时 `AiProviderConfig`（id 只用于报告归属，不落盘）交给
`runAiProviderTest`，回一份与今天完全相同的报告结构，页面复用 `AiTestReport.vue` 渲染。

**为什么不先保存再探测**：保存一份用户还没确认的端点，会在设置里留下一堆半成品，而这个页面从头到尾反对的就是
"页面替用户写下一个他没做过的决定"。

越线的判定照 §7.2 的口径写**一次**（这是本次唯一需要放宽的地方，§8.1 记了它的代价与替代方案）：

> 自动探测**不是**页面加载、渲染、保存或任何其他路径的副作用；它由"用户刚亲手输完一次完整的地址与凭据"这一个
> 输入事实触发，一次输入组合只触发一次，且可被用户的下一次输入取消。

### 4.3 什么时候跑

| 条件                                                                                                                 | 处理                                                                                                                                                                                                                                                                     |
| -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 用户本次已改过**地址、认证方式或凭据三者之一**，且地址通过 `inspectAiProviderBaseUrl`，且（`auth: none` 或密钥非空） | 输入停止 **800 ms** 后触发一次                                                                                                                                                                                                                                           |
| 打开已有端点，或从端点列表切进另一个端点                                                                             | **不触发**：编辑器是被填好的，不是被输入的                                                                                                                                                                                                                               |
| `auth: none`                                                                                                         | 凭据不是条件——地址合法即可触发；但"改过三者之一"这个条件照样要满足                                                                                                                                                                                                       |
| 字段在计时窗口内又变了                                                                                               | 取消本次（清掉计时器），按新值重新计时                                                                                                                                                                                                                                   |
| 地址 / 认证方式 / 密钥与上次触发时完全相同                                                                           | **不重复触发**（一条组合一次）；用户要再探，用模型行上的「重新探测」按钮                                                                                                                                                                                                 |
| 地址不是合法 URL                                                                                                     | **本地拒绝，一个字节都不发**，行上写地址为什么不能用（§3.3 第 1 条）                                                                                                                                                                                                     |
| `forgejoToolkit.aiEnabled` 是 `false`                                                                                | **本地拒绝，一个字节都不发**：宿主在预检的最前面就拒，报告卡说"没有测试：什么都没发"，模型行下面那行状态文字说"探测一个字都没发出去"并指向那张卡。页面**仍然武装**这次探测——"能不能武装"回答的是表单里有没有一个完整的地址与凭据，而"要不要发"是宿主的判断，页面不复制它 |
| 编辑器正在保存 / 正在被移除                                                                                          | 不触发                                                                                                                                                                                                                                                                   |

**"改过三者之一"是一个独立的条件，不是字段值的函数。** 只盯字段值的实现分不清"用户刚输入"和"编辑器刚被填好"，
而这两件事在 `auth: none` 上长得一模一样：不需要凭据，所以一个已存的 `auth: none` 端点一打开就满足了
"地址合法即可"，真实编辑器走查里确实观察到打开编辑器约一秒后自己发出了 `GET /models`，用户一个字都没敲。
所以页面另记一个"本次编辑里这三个字段被改过"的标志（`Settings.vue` 的 `providerDraftEdited`，只由地址
`input`、认证方式 `change` 与凭据 `input` 三个处理器置位，进入与离开编辑器时清零），字段值只回答"组合是什么"。
`auth: none` 的诚实写法因此是：**它不需要凭据，但仍然需要一次编辑**。

`POST /chat/completions` 那一步照旧只属于**显式**的「测试连接」：自动探测只回答"这个端点报出了哪些模型"，它不为
了验证而发内容——这也是它能把"自动"这三个字讲清楚的原因。

### 4.4 失败与空结果

失败**不弹**原生对话框（本页至今一次都没有为设置弹过对话框），而是：

1. 报告卡照常出现，走 `AiTestReport.vue` 的三态标题——"answered" / "failed" / "was not tested: nothing was sent"；
2. 失败原因用**宿主自己的句子**（`openAiEndpointFailure`、`aiProviderProbeDisabledMessage`、`openAiMissingKeyMessage`），
   页面不翻译、不改写；
3. `404` / `405` / `501` 照 `runAiProviderTest` 现有的读法当作"这个端点没有 `/models`"，**不是失败**，报告里说明
   模型要手填；
4. 报告卡下面永远留着「重新探测」这个控件，用户改完地址就能再试；
5. 报告卡自己说它来自哪一边：自动探测的卡与按下的「测试连接」的卡出现在同一个编辑器里，标题又都由同一个结果
   句式和同一个显示名拼成，只有卡上的来源行（`AiTestReport.vue` 的 `source`）能把两张卡分开——真实编辑器走查里
   一张自动的"was not tested"卡正是这样叠在一张显式的"answered"卡下面、看起来像同一张卡出现两次。

### 4.5 自动探测与手写列表怎么共存

结论：**自动探测是预填，手写列表是权威，两者不是两套（§8.7 第 2 条本来就写着"预填"，模型声明不是白名单）。**
具体规则：

1. 探测回来的模型 id **补进**草稿里还没有的行，**不删**用户已经写的行、**不覆盖**已有的显示名；
2. 补进的行是普通行：可编辑、可删除、可改名，和手写的没有区别；
3. 草稿里只有那一行空占位时，先用探测结果**替换**它（现有 `addReportedModels` 的 `placeholderOnly` 处置）；
4. 手写的「添加模型」与「测试连接」两个入口**都保留**：手写是不支持 `/models` 的端点唯一的路，显式测试是自动路径
   失败后的重试；
5. 页面上说清一次探测发生在什么时候，让"列表里的这些行是哪儿来的"有答案：模型行下面一行状态文字
   （"正在探测该端点的模型列表…" / "已从端点的 `/models` 补入 N 个模型，可改可删"，两种语言各一份）；失败与被本
   地拒绝时这一行也必须说话——说出探测没得到应答（或什么都没发）并指向下方那张报告卡。报告卡在模型行下面，常常
   落在折叠线以下，所以失败时留一行空白等于"什么都没发生"（真实编辑器走查里正是这样读的）。
6. 探测成功时，那一行旁边再写一句"这不是同意"（§8 问题 2）：探测只读了模型列表，是否真的会发出内容由
   **AI 总开关**与各功能自己的同意询问决定。它**不进报告卡**：卡是自动探测与按下的「测试连接」共用的组件，
   按来源分支就会改掉"测试连接"那张卡的文案，而那句说明在这条状态行旁边才贴着它刚刚补进的那些行。

## 5. 改进二：id 与显示名的自动生成

### 5.1 生成规则

生成的时机只有一个：**新增模式**（`editingProviderId === null`）下，对应字段为空。生成出来的值就是字段里的值，
用户看得见也改得动，直到端点被存下——存下之后 `id` 才锁定（§5.3），而显示名始终可改。

| 字段   | 从哪儿生成                            | 规则                                                                                                                                                                                           |
| ------ | ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`   | 地址的 **host**                       | 小写；去掉端口；去掉前导 `www.`；把**每一个**不匹配 `AI_PROVIDER_SEGMENT_PATTERN`（`/^[A-Za-z0-9_-]+$/`）的字符换成 `-`；折叠连续的 `-`；去掉首尾 `-`；截到 48 字符；结果为空时退回 `endpoint` |
| 显示名 | 地址的 **host**（含端口，原样、小写） | 例：`forgejo.example.com`、`localhost:11434`；与 id 不同，它不需要是一个合法的密钥段，所以读起来更像用户自己会起的名字                                                                         |

举例（都是占位域名或 `localhost`，符合 `AGENTS.md` 的「Code content」一节）：

| 输入地址                            | 生成的 id            | 生成的显示名              |
| ----------------------------------- | -------------------- | ------------------------- |
| `https://api.example.com/v1`        | `api-example-com`    | `api.example.com`         |
| `http://localhost:11434/v1`         | `localhost`          | `localhost:11434`         |
| `https://www.example.com/openai`    | `example-com`        | `www.example.com`         |
| `http://models.example.com:8080/v1` | `models-example-com` | `models.example.com:8080` |

### 5.2 冲突怎么解决

按**已配置端点列表里所有能读到 id 的条目**（含 `providerEntries` 与 `rejected` 里能读出 id 的那些）去重：

1. 取生成值；若它已存在（比较时忽略大小写，因为 `SecretStorage` 的键区分大小写而用户不会区分），依次试
   `<生成值>-2`、`-3`……直到空闲；
2. 后缀计入 48 字符上限，所以被截断的长 host 也不会因为加后缀而越界；
3. 生成的是**草稿里的字段值**，用户看得见、可以改；页面**不**在后台改名，也**不**在保存时悄悄换一个 id。

### 5.3 id 存下之后不能改，这一点必须在**创建时**说

`providerSecrets.ts` 的模块注释写着这条事实的机制：密钥的键是
`forgejoToolkit.aiProviderKey.<providerId>` 与 `forgejoToolkit.aiProviderHeader.<providerId>.<headerName>`，id 是键的
前半段。所以：

- 编辑器里 id 的字段在编辑态是 `disabled`，旁边写"id 不能改：已存的密钥就是按它做键的"（现页已有
  `settings.aiProviders.editor.idLocked` 这句）；
- **新增模式**要在字段**下方**、紧跟 id 输入框的位置再写一遍，并且说清代价："先想好这个 id。存下之后不能改——
  已存的密钥都按它做键，改了就等于把密钥丢掉。"（新的 i18n 键，两个语言文件同增。）
- 自动生成的 id 因此也要在生成的那一刻就把上面这句摆出来，不能让用户以为"反正是自动的，回头再改"。

## 6. 漂移守卫

### 6.1 要守的是什么

新加一条设置时可能发生的事故只有一种：它**既没有**被页面渲染，**也没有**被列进明确的"只在原生"清单——于是它
静默地不存在于任何用户能找到的地方。§1.3 的表格是给人读的，它拦不住这件事；守卫要拦住它。

### 6.2 守卫的形状

| 项         | 规格                                                                                                                                                                                                                                             |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 测试文件   | `packages/forgejo-toolkit/src/__tests__/settingsSurface.test.ts`（落在扩展套件里：`vitest.extension.config.mts` 的 `include` 是 `src/**/*.test.ts`，`i18nParity.test.ts` 就是在那儿读 manifest 的先例）                                          |
| 读什么     | ① `packages/forgejo-toolkit/package.json` 的 `contributes.configuration.properties` 的**键集合**；② `packages/forgejo-toolkit/webview/src/i18n/en.json` 的**已渲染键清单**——即 `settings.*` 里以 `forgejoToolkit.` 开头的键名；③ §6.3 的策略模块 |
| 策略住哪儿 | `packages/forgejo-toolkit/src/webview/settingsSurface.ts`，导出 `NATIVE_ONLY_SETTINGS`：每条是 `{ key, reason }`。它是页面归属策略的唯一住址；**测试、页面文案、本文都引用它**，谁也不另抄一份                                                   |
| 判定       | 对 manifest 的每一个键：在 `NATIVE_ONLY_SETTINGS` 里（且 `reason` 非空）**或**出现在 ② 里。两者都不占 = 失败；两者都占 = 也失败（说明页面开始渲染它了，策略该更新）                                                                              |
| 失败输出   | 逐条列出违规的键与两个选项，例如 `forgejoToolkit.foo: neither rendered by the settings page nor listed as` `native-only — render it and add its id to the webview string catalogue, or add it to NATIVE_ONLY_SETTINGS with a reason`             |

`NATIVE_ONLY_SETTINGS` **不是**漂移源：一个写错的键不会让测试通过，只会让**真正的**键因为不在清单里而失败，失败
信息里带着那个写错的键不在 manifest 里这一事实（同一测试再断一条：清单里的每个键都必须是 manifest 的键）。

### 6.3 失败信息要能直接照着做

守卫失败时，用户（这里是维护者）需要知道的是"加哪个键、加到哪里"。所以同一测试里再断两条：

1. **已渲染的键必须在字符串目录里按 id 出现**：`en.json` 的 `settings` 段落里该键名作为子串出现（`aiTransport`
   这类短语会因此顺便被守住），且它的值是一个在**两种语言**里都存在的标签键。失败信息给出缺失的键；
2. **已渲染的键不得出现在 `NATIVE_ONLY_SETTINGS` 里**（§6.2 的"两者都占"）。2026-10-06 的修订正是被这一条逼出来的：
   `aiTransport` 回到页面，就必须同时从 `NATIVE_ONLY_SETTINGS` 移走，否则守卫会红。

## 7. 页面不该做的事

1. **不当第二个可写来源**：任何原生设置一旦在页面上有控件，就必须同时从 `NATIVE_ONLY_SETTINGS` 里移走——
   守卫会替我们记住这件事。
2. **不自己定义默认值**：默认值只在 manifest 的 `default` 里写一次；页面显示的是宿主的读数，不是页面常量。
3. **不自己写校验**：id 字符集、URL 合法性、范围、枚举顺序全部来自宿主（`isAiProviderSegment`、
   `inspectAiProviderBaseUrl`、`AI_MODEL_REQUEST_TIMEOUT_*`），页面只在**控件状态**上反映校验结果。
4. **不擅自保存**：自动探测不回写设置、不建端点、不改模型声明以外的东西。
5. **不翻译设置 id**：原生设置的 id 在页面里保持英文原样，用户要拿它去搜。
6. **不回显密钥**：永远不把已存密钥 / header 值读回页面，只显示"已设置"。
7. **不把「打开设置」做成两个都叫这个名字的入口**：本页的入口与原生设置入口必须名字可区分（§2.1）。
8. **不用 `window.alert` / `confirm` / `prompt`**：webview 的既有禁令，设置页也不例外。

## 8. 开放问题

1. **放宽 §7.2 的边界要不要维护者确认？已由维护者确认**，本文的决定是"输完地址与凭据"算一次显式动作。更保守的替代方案是：
   自动路径**从不发请求**，只在用户按下「测试连接」后把报告里的模型自动补进列表（即今天的按钮 + 自动补全）。
   这条替代方案满足不了"进入地址与密钥之后自动探测"的字面要求，所以本文选了前者；代价写在 §8.1。
2. **探测成功要不要在草稿里显式化某个开关？已决定：不显式化任何开关，但探测成功时要说它不是同意。**
   今天的规则是四个独立事实（AI 面是开的、配好端点、存下密钥、同意出网；`ai-model-transport.md` 的 §7.3），自动探测
   **不**改变它对出网同意的影响：探测只探模型列表，不发内容，也不需要任何开关为它打开——这一条本身保持原样。要处理
   的是它读起来像什么：一个用户会从"探测成功了"推出"所以已经同意出网了"。**结论与理由**：① 这是本扩展唯一一处
   "一次动作既证明端点可达、又只读列表"的地方，而"配置/可达不等于同意"是
   [`ai-model-transport.md`](./ai-model-transport.md) 的「7. 同意与外发」一节早已写下的纪律（§7.2"「测试连接」不得被当作
   已经同意出网的证据"、§7.3"「配置好了」不等于「同意出网」"），所以那句提醒不是新口径，只是把它说在用户正在看的那一
   行上；② 探测刚刚替用户补进了模型行，用户下一个动作就是把这些端点接进某个功能，而这正是"我以为已经同意了"最容易
   发生的时刻；③ 代价值得：一句静态说明，不新增控件、不新增状态、不阻塞表单，读者不需要它时可以跳过。**写在哪：**
   落在模型行下面那条状态行旁边（§4.5 第 6 条），**不**落在报告卡里——`AiTestReport.vue` 是自动探测与按下的
   「测试连接」共用的组件，按来源分支就会改掉"测试连接"那张卡的文案；而这条状态行正是 §4.5 第 5 条为"列表里的这些行
   是哪儿来的"设的位置，提醒就贴在它刚写下的那些行旁边。**文案口径：** 只说两件事——探测只读了模型列表；是否会发出
   内容由 AI 总开关与各功能自己的同意询问决定。它**不**说"这个端点不会收到任何东西"（探测本身就是一次请求），也**不**
   由页面读开关状态改写句子（页面不是校验源，句子也不该随一个与探测无关的值漂移）。**不写会怎样：** 用户把一次成功的
   `GET /models` 当成出网许可，直到某个功能拒绝运行才发现没有——而 §7.3 的"配置好了不等于同意"正是为了让这一步不至于
   静默发生。
3. **命令 id 与标题**：`forgejoToolkit.openNativeSettings` 是本文的提案；如果维护者更愿意让现有的
   `forgejoToolkit.openSettings` 接受一个"打开原生界面的哪个筛选"的参数，本文的其余部分不受影响。
4. **`aiPreReviewPromptScope` 的五段文案**是不是要逐字与 `package.nls*.json` 的 `enumDescriptions` 同义？本文定为
   "同义不逐字"（页面要更短），是否接受由维护者定。
5. **通知区块的落点**：现在 Dashboard 只用 `notificationPollingEnabled` 解释角标；若这一条真的上页面，
   Dashboard 那句解释要不要改成指向设置页的一行链接？**已决定：不加这个链接，Dashboard 侧什么都不改。** 先要说清
   这个问题的指称——Dashboard 上并没有一处"角标说明"的界面：那句话是 `Dashboard.vue` 的代码注释、`Settings.vue`
   通知区块的注释，以及 [`multi-window-polling-lease.md`](./multi-window-polling-lease.md) 的「2.1 选项
   `forgejoToolkit.multiWindowLease` 的用途与用户可见语义」一节里"徽标/列表可能少一次自动更新"这条已知代价；用户
   能读到的只有设置页的开关与两段说明（`settings.notifications.disabledHint`、`settings.multiWindow.*`）。理由：
   ① **没有可链接的行**：要从 Dashboard 指过去，就得先新造一行说明——那是新界面，不是"加个链接"这一点改动，而且
   会在两个地方各解释一遍同一个开关；② **最需要解释的那个状态在 webview 里读不到**：租约开启时"本窗口不是轮询窗口"
   只有宿主知道（`LeaseSupervisor` 的 role），webview 消息面里没有这个字段，所以能写出来的只有"轮询可能被关掉或用
   了租约"这种不点名的句子；③ **不点名的句子会误导**：角标静默的两种原因（用户自己关了轮询 / 本窗口不持有租约）
   对策相反——一个是去打开开关，另一个是把开关保持原样——一句通用链接会把用户推去改一个工作正常的设置；④ 这条代价
   已按设计本身缓解：租约的焦点跟随把提示与轮询拉回用户正在用的窗口，机制降级时 `leaseDegradedNotice` 一次性弹出
   提示并带「Turn Off in This Window」这个设置级回退，剩下的"少一次自动更新"是"手动打开通知视图仍即时读取"的
   已知代价（上引记录 §2.1）。本决定不改任何用户可见行为，因此不进 `FEATURES.md`，也不进两份 `CHANGELOG`。
6. **`reason` 字段要不要中文**？`NATIVE_ONLY_SETTINGS` 的 `reason` 是给维护者读的（测试失败信息），本文定为
   **英文**，与测试面的其余注释一致；页面上的"更多设置"指针不复用它，而是走 i18n 键。
7. **`aiTransport` 该不该在页面上有控件，以及 `auto` 下"用不到"的那一半要不要藏起来？已由维护者决定（2026-10-06）：
   两件都做。** 原来把它留在原生界面的理由是"三值枚举原生下拉表达得更好、页面渲染就要处理控件弹回"，维护者否掉了
   这个权衡：这个选择决定 AI 区块呈现哪一半配置（"选了编辑器模型却还看到一整块端点配置"读起来像页面没说真话），
   而一个决定这一页长什么样的选择放在另一页上，等于要求用户在两页之间来回推理。于是 ① 它回到页面，用共享枚举
   `AI_TRANSPORT_CHOICES` 渲染三值下拉；② 页面按选择裁剪：`vscode-lm` 只留编辑器的聊天模型行、`openai-compatible`
   只留端点面、`auto` 两者都留并写一句优先级。**两条边界是这次裁决的一部分**：裁剪只针对这一选择**用不到**的那一半，
   并且每一个被裁掉的位置都留一句"为什么"和"改哪个控件拿回来"，控件本身永不隐藏；请求超时与逐功能覆盖**不参与裁剪**
   ——超时也管覆盖，覆盖的端点下拉也要能选到刚配好的端点。漂移守卫随之更新：`aiTransport` 从 `NATIVE_ONLY_SETTINGS`
   移入已渲染集合，§2.2 的指针行删除（一个值只能有一个可写控件，§1.1 第 3 条）。
8. **全局 AI 开关要不要让关掉它的那片配置留在页面上？已由维护者决定（2026-10-06）：要留，而且不能禁用。**
   这一条是 §1.1 第 3 条的直接推论：那些控件（功能开关、提示词范围、传输方式、端点面、超时）在本页之外没有第二个可写
   来源，跟着它们的总开关一起隐藏或变灰，就等于把"重新打开 AI 之后要用的东西"藏起来。页面因此只做两件事：在开关那一
   行说清关掉意味着什么与怎么打开（§3.3 第 2 条），并在 §9.3 的区块里重复同一句（那一块渲染的是宿主的 `capability`
   读数，与开关来自两条不同的消息，读的时刻也不同，所以这一句在两边都写）。

### 8.1 自动探测的代价（写在明处的取舍）

`ai-model-transport.md` 的 §8.7 把「测试连接」定为"唯一会给端点发内容的自动动作，且由一次显式点击触发"。本节
的自动探测**不**发内容（只 `GET /models`），但它确实是本扩展里第一处"用户没有点任何按钮，就有请求离开机器"的
路径。代价是：一个地址写错、恰好指向第三方服务的用户，会在补全密钥后就向那个地址发一次 `GET /models`。缓解是
"一次输入组合一次、800 ms 静默后、可被下一次输入取消、本地先校验（含全局 AI 开关）、失败不弹窗"；如果维护者认为这
仍然越线，§8 问题 1 的保守替代方案是现成的退路。

### 9.3 交互：设置页住进编辑器区的一个标签页，导航按宽度给两种形态

**决定一：这个面的家是编辑器区的一个标签页（tab），不是侧边栏里的一个视图。**

它凭什么赢过"留在侧边栏"：

1. **这是一个表单面。** 十一块里有 13 个复选框、9 个下拉、15 个文本字段（§9.1）；侧边栏那一列本来是为"列表 + 一个
   详情"设计的（仪表盘、通知），塞进一张长表单之后两者都变差。
2. **编辑器自己的设置就住在标签页里。** 用户对"设置"这件事的心智模型由 VS Code 原生设置编辑器立好了：一个标签页、
   一列分组、一列内容。把我们的面放进同一个形状，用户不需要重新学。
3. **设置不再挤掉仪表盘。** 今天打开设置是 `router.push({ name: 'settings' })`——**同一个 webview 内部换路由**——
   所以看设置就必须离开仪表盘、通知或 PR 详情；标签页与它们是并排的，可以同时开着。
4. **单实例的生命周期在标签页上更干净。** 侧边栏视图是窗口级的一列，"打开设置"要么把它抢过来、要么把它推上去；
   标签页有现成的 `createOrShow` + `currentPanel` 语义（`OnboardingWebviewPanel` 就是这个形状），"只开一个、再开
   就聚焦"是它的默认行为。**这就是那条"原来打算把设置页留在侧边栏、把编辑器区默认列为不做的事"被撤掉、换成这条
   决定的理由**：那件事现在是主路径，不再是备选。

**单实例与再打开的语义（写死）**：

- **一个窗口一个标签页。** 打开用既有的命令 `forgejoToolkit.openSettings`（命令面板与侧边栏视图标题栏那个齿轮动作
  都还是它）；第二次打开是 `reveal`——聚焦已经开着的那一个，**不叠第二个**。
- **标签页还活着、重新显示时**（切回来，或被别的标签页盖住后再露出）：宿主在它重新可见时推一份**新读数**（设置
  快照、实例、端点、工作树、模型列表），而不是让页面带着旧快照回来。这与 §3.1 第 4 条同源——页面永远不显示一个不是
  刚刚从宿主读来的状态。
- **标签页被关掉之后再打开**：那是一个**新的页面**，从挂载开始重新读一遍，**什么都不保留**——包括**上次在哪一组**
  （§9.4 第 5 条记的状态是"这个标签页活着这段时间"的）。代价是重开回到默认组（§9.6 问题 3），换来的是"页面上看到的
  永远是这个窗口此刻的读数"。

**侧边栏保留入口，设置面从侧边栏退役（要在代码里做干净，不能两处都留）。** 今天的事实是：侧边栏视图
`forgejoToolkitView` 是**一个** webview，跑 `App.vue` 与它的 router；设置是那个 router 里的一条路由——宿主
`ViewProvider.openSettings()` 先 `_revealView()` 把侧边栏显示出来，再 `postMessage({ command: 'openSettings' })`，
webview 侧 `case 'openSettings'` 做 `router.push({ name: 'settings' })`。所以**侧边栏视图今天确实带着设置状态**，
而这条路由要退役：

- 命令 `forgejoToolkit.openSettings`（命令面板）与 `view/title` 里那个 `$(gear)` 动作**保留**，两者都改成**打开 /
  聚焦标签页**；
- `ViewProvider.openSettings()` **不再** `_revealView()`：打开设置不该把侧边栏抢过来（那会把仪表盘换下去）；
  `openDashboard` 等其余命令的 `_revealView()` 照旧；
- webview 侧那条 `case 'openSettings'` 与侧边栏 router 的 `settings` 路由**删掉**，`Settings.vue` 不再由侧边栏这一份
  应用渲染——同一批"只有本页才写得了"的控件永远只在一处渲染（§1.1 第 3 条、§7 第 1 条）；
- 侧边栏视图此后做的事**除设置面以外一件不少**：仪表盘、通知、仓库与 PR 详情、工作树入口都留在原处。

**实现注记（不是决定；决定只是"这个面住在标签页里"）**：一个标签页需要它自己的 webview 面。这个仓库的 webview 构建
**按面**发一份 HTML 文档 + 一个入口（`webview/vite.config.mts` 的 `SURFACES`，宿主侧 `src/webview/content.ts` 的
`WEBVIEW_HTML_FILES` / `panelMode`），并且构建时断言一个 panel 面**不许**碰到 `vue-router`；而 `Settings.vue` 今天
**import 了 `useRouter`**（导入预览的转场 `router.replace({ name: 'importPreview' })`，以及导入完成后回仪表盘的
`router.replace({ name: 'dashboard' })`）。所以这个标签页的面要么注册成一个 dashboard 类面（带上 `App.vue` 与
router，等于把仪表盘外壳搬进标签页），要么先把 `Settings.vue` 的 router 依赖摘掉、再注册成 panel 类面（像
`onboarding.html` / `OnboardingPanel.vue` 那样自带一个根组件），外加一条按面的图断言。这些都是实现的形状，选哪条不
影响本节的决定。

**决定二：标签页内部的导航按页面自己量到的宽度给两种形态，自动切换，不新增用户设置。**

三个候选的取舍写在明处：

1. **竖向导航列表**（编辑器自己的设置就是这个形状）——**它需要宽度，而标签页正好给了宽度**：VS Code 的活动栏是
   窗口级的一列，永远在那里；页面在**约 297 px 的侧边栏**里再加一列导航，就是在那个宽度里塞**三**列（活动栏、我们的
   导航、内容），内容只剩约 150 px，比一列长滚动更坏。所以在侧边栏里它不成立、在标签页里它成立
   （[`tools/ui-review/README.md`](../../tools/ui-review/README.md) 量到的编辑器区面板约 890 px）。**"三列"从此只是
   窄的那一态的问题**：标签页被拖窄，或者被拆到分割编辑器的一格里。
2. **吸顶标题里的分组选择器**（`vscode-single-select`，页面已经用它渲染枚举；或一个分段控件）——不新增任何列，最窄
   也能用，所以它是标签页**变窄时的退路**，不是基准。
3. **横向标签条**——**否掉**：六七个中文标签在窄宽度下放不下（最长的组名与「AI：Pull Request 描述」都在十个字
   上下），它只会换行或横向滚动，而横向滚动正是这一页其余每一处用 `flex-wrap` 与 `overflow-wrap: anywhere`
   刻意避开的失败。

|          | 宽形态（标签页的常态）                               | 窄形态（标签页被拖窄，或落在分割编辑器的一格里）             |
| -------- | ---------------------------------------------------- | ------------------------------------------------------------ |
| 形状     | 竖向导航列表（六个组名），与编辑器自己的设置同形     | 吸顶标题里一个分组选择器（`vscode-single-select`），不新增列 |
| 为什么   | 标签页是这一页唯一的导航列，宽出来的空间正好给内容列 | 内容恒为一列，第三列的问题在那一态里根本不存在               |
| 必须成立 | 当前组有可见的选中态；切换后内容真的换了一组         | 选择器完整可读可操作；内容恒为**一列**、没有页面自己的导航列 |

**宽度从哪来：复用页面已经有的那次尺寸观察，不新开第二个观察者。** 页面今天为吸顶块做过一次尺寸观察：
`stickyHeightObserver`（一个 `ResizeObserver`）观察编辑器吸顶块 `editorHeading`，把它的 border-box 高度写进
`editorStickyHeight`（`syncEditorStickyHeight`），列表态没有这个元素时它 `disconnect()` 并把高度归零。所以实现要
把**同一个** `ResizeObserver` 的观察目标加上页面的滚动根（`.settings`），从同一份 entry 的 border-box **行内尺寸**
读宽度：一个观察者、两份读数（宽度判形态，高度喂 `scroll-padding-top`）。新加第二个 observer 明确否掉——两个观察者
对同一个盒子报两次尺寸，正是这一页最不需要的那种"两个来源"。宽度必须**在两个编辑器态里也读得到**，否则从端点编辑器
返回时形态会跳。

**阈值：`532` px，2026-10-06 实测后写死进本节。** 判据不是"标签页一律宽"，而是"两列必须比一列更好"：内容列的地板
取这一页被设计时用的默认面板宽 **358 px**（`Settings.vue` 的样式注释里就记着"约一像素宽于其所在列 at the default
358 px panel"），导航列取实测宽度 **150 px**，加上列间距 **24 px**，三者相加得 **532**。实现在
`webview/src/views/settingsGroups.ts` 的 `WIDE_NAV_MIN_WIDTH`，判据是页面自己量到的宽度（见上一段）。

实测（2026-10-06，隔离 dev host，2560×1392 视口，devicePixelRatio 1）：

| 页面宽度                      | 形态 | 同一次读到的数字                                                               |
| ----------------------------- | ---- | ------------------------------------------------------------------------------ |
| **914 px**（标签页常态）      | 宽   | 导航列 150 px、内容列 740 px、`role="tablist"` 竖向、无选择器                  |
| **1866 px**（编辑器组最大化） | 宽   | 导航列 150 px、内容列 1692 px、无选择器                                        |
| **531 px**（分割编辑器一格）  | 窄   | 无导航列、单个内容列 531 px、吸顶选择器条 34 px、`scroll-padding-top` 34 px    |
| **300 px**（侧边栏量级）      | 窄   | 无导航列、单个内容列、`clientWidth == scrollWidth`（不横向溢出）、吸顶条 34 px |

531 与 914 把阈值夹在中间；531 → 300 与 300 → 1866 → 300 两次改宽都观察到形态跟着切换且不来回抖。**窄的一侧**的
参照仍是侧边栏帧 **233 px** 与更宽窗口下的 **297 px**
（[`tools/ui-review/README.md`](../../tools/ui-review/README.md)）——它们正是"第三列放不下"的宽度，也是把标签页拖窄、
或塞进分割编辑器一格时的量级。阈值以一个**数字**写进本节，不留给实现者猜（§9.6 问题 4）。

**实现注记（导航控件：宽形态怎么搭、以及为什么不用 `vscode-tabs`）。** 组件库里的 `vscode-tabs` 是**横向**标签条，
没有竖向呈现：窄形态下六七个中文标签放不下，宽形态下它也不是设置页要的形状——所以**分组导航不用它**（它仍留给将来
真正需要横向标签的地方）。宽形态的导航列表是**页面自己的一小块组件**：

- **语义**：`role="tablist"` 带 `aria-orientation="vertical"`，每个组一个 `<button role="tab" aria-selected>`，
  内容区是一个 `role="tabpanel"` 并由当前那个 tab 标注（`aria-labelledby`）。
- **外观**：只用编辑器列表那几个主题变量（选中 / 未选中 / hover / 焦点边框），看起来就是编辑器自己的设置导航，
  不引入自定义品牌色。
- **键盘**：roving tabindex；`↑` / `↓` / `Home` / `End` 移动，`Enter` / `Space` 激活。
- **明确不用的两个近亲**：`vscode-radio-group`（它的语义是"选一个值"、渲染成单选圆点、键盘模型也不同）与树组件
  （六个组是**平级**的，不是层级）。

窄形态继续用页面已经在用的那个单选下拉（`vscode-single-select`），放在吸顶标题里，不新增列。**两种形态共用同一个
"当前组"状态**，区别只在呈现（§9.4 第 1 条：换形态不改变任何控件的可见性或可写性）；切换由页面自己量到的宽度驱动
（见上）。

**实现时先去量组件库里实际装着的那个版本的 API，别信文档页**：如果现用版本已经提供竖向或列表式的呈现，优先复用它
而不是新写一个；这次检查是实现的一部分（记在这里，免得重新发现一遍）。

### 9.4 不得回退

1. **没有死路：六个组都在选择器里，点一次就到；一个控件的唯一可写来源必须仍然够得着。** 尤其 `aiEnabled` 那条
   "永不隐藏、永不被它自己关掉的东西禁用"（§3.2），以及"关掉总开关不隐藏也不禁用功能面与端点面"（§3.3 第 2 条）：
   分组只决定同一时刻呈现哪一组，不改变任何控件的可见性、可写性，也不改变它是唯一来源这一点。任何一个只有本页才
   写得了的值，都不许因为切组而变得不可达。**推荐十一块全部保持挂载、非当前组用 `hidden` / `inert` 隐藏**——`hidden`
   同样把它移出 Tab 顺序，也就是那两个编辑器态当初用 `v-if` / `v-else` 而不是 `v-show` 要保住的性质；理由与这一条的
   代价见 §9.7 的「挂载与守卫」一行。
2. **漂移守卫照旧。** `settingsSurface.test.ts` 判的是"这条设置有没有被渲染"，不是"哪一组渲染它"：它读 manifest 的
   键、`en.json` 的键与 `Settings.vue` 的**模板文本**，所以分组怎么切都不影响它，它必须**不加改动**继续通过。它依赖
   的两处形态要在实现里保住：指针行渲染的两个 id、以及 `useMockApi` 在模板里不出现——两条都靠"这些文字在
   `Settings.vue` 里"。把任何区块拆成子组件会让守卫读不到它们（它会静默放过，而不是报错），所以要么不拆，要么在
   同一次改动里把守卫的读取面一起扩。**不过**：任何按**渲染结果**判断的检查——包括页面自己的挂载式套件与 §9.7 新增的
   映射断言——不能只看当前那一组，否则它会从"通过"变成"静默空转"；这条见 §9.7 的「挂载与守卫」一行。
3. **两个编辑态记得自己从哪一组打开，并回到那一组。** 实例编辑器从「实例」开，端点编辑器从「AI 端点」开，返回后
   停在同一组。回程的落点照旧是原来那一行的「编辑」按钮（`listTarget` 与 `instanceEditButtonRef` /
   `providerEditButtonRef` 的 `FocusHandoff`），所以"回到哪一组"和"焦点交给谁"必须是同一次动作：先回到组，再把焦点
   交给那一行。组没回来、焦点落在一个不在屏幕上的控件上，就是死路。
4. **吸顶标题、滚动留白、焦点交接与换行照旧，并且在窄宽度下继续成立。** `.editor-heading` 的 `position: sticky` +
   `top: 0` + 不透明背景、`scroll-padding-top: var(--editor-sticky-height)`、`scheduleFocusAttempt` 的三帧重试与
   `cancelFocusHandoff`、页头与已保存行的 `flex-wrap`、说明文字的 `overflow-wrap: anywhere`——都在原处。新形态只多
   一个吸顶块（列表态的组选择器条；两个编辑器态里选择器并进**已有的**那个吸顶块，不新起第二个吸顶条），它的高度必须
   进同一个 `--editor-sticky-height` 读数，否则被聚焦的字段会落到它下面——那正是 54 px 那个缺陷的形状。
5. **页面记住用户上次在哪一组：会话内的状态**（`Settings.vue` 里一个 `ref`；这里的"会话"就是**这个标签页从打开到关掉**
   的那段时间，标签页关掉即丢，§9.3），**不是存下来的设置**。理由：
   ① §1.1 第 3 条与 §6 的守卫模型只有两种身份——"被本页渲染的设置"与"明确只在原生的设置"；一个纯导航偏好两条都不
   占，写成 manifest 键会让守卫的 25 条账目多出一个与用户无关的键，写进 `NATIVE_ONLY_SETTINGS` 又会让那张表的理由从
   "用户不该看见的设置"变成"我们记不住 UI 状态"。② 页面至今不是它自己的设置源（§7 第 2、3 条），为一条页面内部偏好
   开第二个作用域，正是这一页一直在防的事。③ 需要跨标签页关闭记住的场景还没有出现，重开回到第一组是可接受的代价；
   webview 至今没有任何 `setState` / `getState` 调用（全仓只有 `acquireVsCodeApi()`）。默认落在哪一组是 §9.6
   问题 3。

### 9.5 这次明确不做的事

1. **不做搜索框。** 按名字过滤需要一份索引、要对翻译后的标签匹配、要一个"没有结果"态，而且它回答的是"我知道我要
   找什么"；这一页今天的问题是"我不知道这里有什么"，那是导航不是搜索。留作独立议题。
2. **不在组内再折叠。** 分组的粒度就是折叠的粒度；组内再折一次会把控件藏到第二层，违反 §9.4 第 1 条。
3. **不在标签页之外再留第二份设置面**（侧边栏的设置路由退役，见 §9.3）。两处渲染同一批"只有本页才写得了"的控件，
   正是 §1.1 第 3 条与 §7 第 1 条禁止的。
4. **不新增任何设置**：形态与阈值都是自动的，没有"布局"开关（理由同 §9.4 第 5 条）。
5. **不动 §1–§8 的归属规则**：谁该上页面、谁是唯一可写来源、指针行怎么写，都不因分组或换家而变；分组只处理"已经在
   页面上的东西放在哪儿"。
6. **不把 `服务器版本` 搬出实例编辑器**：它是实例记录的一个字段（`declaredServerVersion`），不是一个区块。
7. **不改 `forgejoToolkit.openSettings` 的命令 id 与标题**：它今天的语义就是"打开本页"（§2.1 已经决定过不把它改成
   打开原生设置），搬进标签页只是换它打开的落点。

### 10.2 宽度阈值：谁量的、量到什么、数字怎么来

| 项         | 内容                                                                                                                                                                                                                                                                                                        |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 问题       | §9.3 只给了"约 500 px，实现时实测后写死"。数字要能经受"两列必须比一列更好"的判据，测量还必须复用页面已有的那次尺寸观察。                                                                                                                                                                                    |

| 选了       | **①**，阈值 `WIDE_NAV_MIN_WIDTH = 532`（`webview/src/views/settingsGroups.ts`）。② 正是 §9.3 明确否掉的"两个观察者对同一个盒子报两次尺寸"；③ 量的是窗口不是页面，标签页被拆进分割编辑器一格时窗口宽度不变而页面宽度变了，判据会失效。                                                                       |
| 为什么 532 | 导航列实测 **150 px**、列间距 **24 px**、内容列地板 **358 px**（页面自己的样式注释就写着它按 358 px 面板设计），三者相加 = 532。实测把阈值夹在中间：页面 531 px 时是窄形态，914 px 时是宽形态（测量明细见 §9.3 的表）。                                                                                     |
| 改回哪里   | 若维护者认为宽形态可以在内容列 346 px（即阈值 520）时就出现：把 `WIDE_NAV_MIN_WIDTH` 改成 520。若想要更窄的导航列：`.settings-nav { flex: 0 0 140px }` 与常量一起降到 522（140 + 24 + 358）。若想让用户自己选：那要新增一条设置，而 §9.4 第 5 条与 §9.5 第 4 条都明确说不新增设置，改这条要连 §9.5 一起改。 |

**走查没能跨过的那一步，写在这里**：harness 的坐标守卫拒绝一个"终点落在 webview 帧之外"的拖拽，所以把标签页从窄**拖宽**
到阈值附近做不到——帧一窄，右侧的分隔条就在帧外了。阈值两侧因此是用另外两个方向证的：页面 531 px（窄）与 914 px（宽）
把 532 夹住；以及把编辑器组最大化到 1866 px 再还原到 300 px，两个方向都观察到形态跟着切且不来回抖。

### 10.3 首屏渲染哪一组，以及它与"保持挂载"的关系

| 项       | 内容                                                                                                                                                                                                                                                                                                                                       |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 问题     | 六个组里首屏渲染什么、其余五组是挂着还是卸掉。§9.4 第 1 条推荐"十一块全部保持挂载、非当前组用 `hidden` / `inert` 隐藏"，但没说首屏那一帧是什么。                                                                                                                                                                                           |
| 选项     | ① 首屏渲染**当前组（默认「通用」）**，其余五组照常挂载但 `hidden` + `inert`；② 首屏只挂载当前组，切到哪组才挂载哪组；③ 首屏全部挂载且全部可见，靠 CSS 逐组隐藏。                                                                                                                                                                           |
| 选了     | **①**，`.settings-pane[hidden] { display: none }` 是必须的那一行（面板是 flex 容器，作者写的 `display` 会盖掉浏览器对 `[hidden]` 的规则），`inert` 让非当前组不可聚焦、也不被读屏读到。                                                                                                                                                    |
| 为什么   | ② 会让页面自己的套件与漂移守卫的"渲染结果"那一半**静默空转**——它们在一次挂载里跨组查询控件（`#notification-polling-enabled`、`#mcp-*`、`#ai-enabled`…），卸掉就查不到，测试从"通过"变成"什么也没检查"。③ 首屏就会把六组内容一起画出来，切换的语义也没了。① 是 §9.4 推荐的那条，且"首屏 = 默认组"只是"五个非当前组"的特例，没有第二套规则。 |
| 改回哪里 | 若维护者愿意承担"守卫遍历六个组"的改造（把 `Settings.settingsSurface.test.ts` 改成逐组挂载、并给漂移守卫的渲染面配一条遍历全部六组的断言），② 是可行的；那是一次测试面的改造，不是页面的一行改动。                                                                                                                                         |

### 10.4 两个编辑器的"回到原组"是怎么成立的（以及为什么编辑态里没有导航）

| 项       | 内容                                                                                                                                                                                                                                                                                                                                                                                                                  |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 问题     | §9.4 第 3 条要求"实例编辑器从「实例」开、端点编辑器从「AI 端点」开，返回后停在同一组，并且焦点回到那一行的「编辑」按钮"。§9.4 第 4 条的括号里还写着"两个编辑器态里选择器并进已有的那个吸顶块"。                                                                                                                                                                                                                       |
| 选项     | ① **不动组状态**：编辑器打开时 `currentGroup` 不改，关闭后它自然还是原来那组，焦点交给原有的 `FocusHandoff`；编辑态**不渲染**任何分组导航。② 编辑器打开时记下组、关闭时写回，并在编辑态的吸顶标题里放一个分组选择器，选中别的组就先关编辑器再切组。                                                                                                                                                                   |
| 选了     | **①**。它把"回到哪一组"做成结构性事实而不是第二套机制：组状态从未被改过，所以"回到原组"与"焦点交给那一行"是同一次动作的两个面（组没变 → 那一行还在当前组里 → `listTarget()` 找得到它）。                                                                                                                                                                                                                              |
| 为什么   | ② 的分组选择器在编辑态里只有一个有意义的语义——**离开编辑器**；而实例编辑器里可能有用户刚敲进去的字段，离开要经过 `requestCloseEditor` 的丢弃确认，于是"切组"要么变成一次带确认的关闭（一个导航控件触发数据丢失对话），要么在用户取消后变成一个按了没反应的控件。两者都比"编辑态暂时没有导航"更坏。§9.3 没有规定编辑态必须能切组，§9.7 的验收行要求的是"返回后停在原组 + 焦点落在原来那一行的编辑按钮上"，两条都成立。 |
| 改回哪里 | 若维护者要按 §9.4 第 4 条的括号实现：在 `.editor-heading` 里加一个 `vscode-single-select`（窄形态）并复用 `currentGroup`，`selectGroup()` 改成"先 `requestCloseEditor()`/`requestCloseProviderEditor()`，确认关闭后再切组"，同时把 `pendingGroupAfterClose` 的取消路径写清（用户拒绝丢弃时不能切组）。宽形态下编辑态没有导航列，所以那条改动只影响窄形态。                                                            |

### 10.5 "重新显示时推一份新读数"的实现形状

| 项       | 内容                                                                                                                                                                                                                                                                                                                                                    |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 问题     | §9.3 要求"标签页还活着、重新显示时，宿主推一份新读数（设置快照、实例、端点、工作树、模型列表）"。宿主可以把这些读数**自己拼成消息推下去**，也可以推一个"去读"的信号让页面用它已有的请求再问一遍。                                                                                                                                                       |
| 选项     | ① 新增一条 `refreshSettings` 消息，宿主只推"重新可见"这个事实，页面收到后重新发它原本就在挂载时发的那些请求（`getInitialState` + 设置快照 + 端点快照 + 模型列表）；② 宿主把四份读数的消息各自组装好推下去；③ 页面自己监听 `document.visibilitychange`。                                                                                                 |
| 选了     | **①**。`useAppState` 的 `refreshSettings` 分支做两件事：重发 `getInitialState`，并把 `settingsRefreshTick` 加一；页面 watch 这个计数，重跑 `reloadSettingsPage()`（挂载时用的同一个函数）。                                                                                                                                                             |
| 为什么   | ② 会把每份读数的组装逻辑抄第二遍（端点快照的读取涉及密钥存储、模型列表要问 `vscode.lm`），而"页面只显示它刚被宿主告知的状态"这条纪律要求读数只有一条实现；③ 在保留上下文的 webview 里不可靠（帧被隐藏时浏览器不一定发这个事件），而且会让页面自己去猜"我什么时候该重新读"。为什么用计数而不是布尔：第二次、第三次重新显示都要重读，布尔要有人把它清零。 |
| 改回哪里 | 若维护者更愿意看到"宿主把读数直接推下去"：删掉 `HostToWebviewMessage` 里的 `refreshSettings`，在 `settingsPanel.ts` 的 `refresh()` 里改成推 `initialState` 的载荷与三份快照（端点快照可直接复用 `_pushAiProviderSettings()`，设置快照复用 `_readSettingsSurface()`，模型列表要新写一个推送分支，因为页面现在是从请求的返回值里取它的）。                |

| 导入预览的去处               | §9.3 只说了"侧边栏的设置路由退役"，没说**导入预览**（侧边栏 router 的 `importPreview` 视图）怎么办——它是设置页唯一会导航去的地方。选项：① 把标签页里的预览**就地渲染**（`Settings.vue` 的 `<ImportPreview v-if="state.importPreview.value" />`），② 让宿主把侧边栏揭开并导航到那条路由，③ 给导入预览也新建一个 panel 面。**选了 ①，并把侧边栏那条 `importPreview` 路由一并退役**（推理：只有设置页能到达它；留着它就是同一份预览在两个面各有一份代码与一份文案）。代价：`ImportPreview.vue` 的两处 `router.replace({ name: 'settings' })` 删掉，它不再需要 router；`Onboarding.vue` 里那条"非 panel 模式就 push 到 importPreview"的死分支也删了。若维护者要 ②：`ImportPreview.vue` 的关闭路径改回 `router.replace`，并在宿主里给侧边栏加一条"打开导入预览"的消息与 `_revealView()`。 |

### 10.7 走查证据（2026-10-06，隔离 dev host）

- **两个入口**：命令面板的 `forgejoToolkit.openSettings` 与侧边栏视图标题栏的齿轮都在**同一个** webview（`44bc6a1b…` /
  重载后的 `6fd4d7a3…`）上聚焦已开着的标签页；编辑器区始终只有一个 `where: editor` 的帧，侧边栏帧的 id 与内容全程不变。
- **宽形态**（页面 914 px）：`role="tablist"` + `aria-orientation="vertical"`，六个 `<button role="tab">`，被选中的那个
  `aria-selected="true"` / `tabindex="0"`、其余 `-1`，`aria-controls` 指向对应窗格；导航列 150 px、内容列 740 px、无选择器。
- **窄形态**（页面 300 px 与 531 px）：没有导航列、单个内容列、吸顶选择器条 34 px，且 `--editor-sticky-height` 与
  `getComputedStyle(.settings).scrollPaddingTop` 都读到 `34px`；`clientWidth == scrollWidth`（不横向溢出）；六个选项齐全，
  选中即换组。
- **保持挂载**：任意时刻六个 `.settings-pane` 都在文档里，五个 `hidden` + `inert`；`#notification-polling-enabled` 等跨组控件
  始终查得到（与页面套件一致）。
- **编辑态返回**（窄形态实走）：从「实例」进编辑器时 `--editor-sticky-height` 变成标题块的 `108px`，关闭后回到吸顶条的
  `34px`，「实例」窗格重新可见，`document.activeElement` 是那一行的「编辑实例」按钮。
- **重新显示重读**（用一个配置变更监听不推送的设置 `forgejoToolkit.worktreeOpenMode` 做对照）：标签页可见时改设置，页面仍显示旧值
  （说明这条路径没有被推送掩盖）；再**聚焦已开标签页**（命令面板）或让它**重新可见**（切走再切回）后，页面显示新值。
- **跨阈值**：300 px → 1866 px（最大化编辑器组）→ 300 px，形态跟着切、不来回抖，组状态跨切换保留。
